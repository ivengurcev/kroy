# Запчасти: обнаружение и контракт полей

**Статус:** обнаружение запчастей и извлечение полей уже реализованы в прототипе. Ниже сначала описано существующее поведение, затем ограничения.

## Что считается запчастью

Запчасть — обычный React-компонент. Специальный базовый класс, регистрационный вызов или отдельный Yarn Workspace не нужны. Общие компоненты, не являющиеся запчастями, располагаются вне `parts/`, например в `layout/`.

Генератор: `scripts/discoverParts.mjs`. Он рекурсивно обходит `parts/`.

1. **Каталог с `package.json`** — одна запчасть, даже если внутри несколько файлов. Входной файл задаётся `main`. Явное `name` имеет приоритет; без него имя формируется из пути. Внутрь такого каталога поиск других запчастей не продолжается.
2. **Каталог без `package.json`** — только контейнер. Каждый найденный файл `.jsx` — отдельная запчасть с именем, сформированным из пути.
3. Файлы `.jsx` непосредственно в `parts/` тоже считаются запчастями.

## Именование

- Директории именуются строчными буквами в `kebab-case`.
- React-компоненты и их файлы именуются в `PascalCase`; обычные JS-модули — в `camelCase`.
- Идентификатор запчасти начинается с `@kroy/`, каждый последующий сегмент записывается в `kebab-case`.
- Сегменты имени, сформированного из пути, нормализуются автоматически.
- Явное `package.json.name` не нормализуется и должно уже соответствовать формату.

Примеры:

| Путь | Имя |
|---|---|
| `parts/Gallery.jsx` | `@kroy/gallery` |
| `parts/GallerySimple.jsx` | `@kroy/gallery-simple` |
| `parts/section/Main.jsx` | `@kroy/section/main` |
| `parts/section/subsection/package.json` без `name` | `@kroy/section/subsection` |
| `parts/contacts/package.json` с `name: "@kroy/contacts"` и `main: "Contacts.jsx"` | `@kroy/contacts` |

Генератор проверяет формат и коллизии итоговых имён, в том числе возникшие после нормализации, существование входного файла и выход `main` за границы каталога. Наличие JSDoc **не определяет**, является файл запчастью или нет.

## Описание редактируемых полей

**Единственный источник контракта полей — JSDoc в исходнике компонента.** Обычные `@param` описывают имена, типы и подписи. Теги `@kroy` настраивают виджеты и ограничения редактора.

~~~jsx
/**
 * @param {object} props
 * @param {string} props.phone - Телефон
 * @param {{name: string, link: string}[]} props.socials - Социальные сети
 *
 * @kroy phone widget=tel format=ru
 * @kroy socials.name maxLength=30
 * @kroy socials.link widget=url
 */
export default function Contacts({ phone = '', socials = [] }) {
    return (
        <div>
            <a href={phone}>{phone}</a>
            {socials.map(({ name, link }) => (
                <a key={name} href={link}>{name}</a>
            ))}
        </div>
    );
}
~~~

Поддержка текущего парсера `scripts/parsePartDoc.mjs`:

| JSDoc-тип / настройка | Схема редактора |
|---|---|
| `string` | `input` |
| `number` | `number` |
| `boolean` | `checkbox` |
| `'one'\|'two'` | `select` с вариантами |
| `{name: string, link: string}[]` | `list` со вложенными полями |
| `@kroy field widget=textarea` | `textarea` |
| `@kroy field widget=tel` | `input` с телефонным типом ввода |
| `@kroy field widget=url` | `input` с типом URL |
| `@kroy field maxLength=30` | ограничение длины |
| `@kroy field format=ru` | метаданные формата |

Настройки допускают вложенный путь (`socials.link`) и применяются к каждому объекту массива. Они не меняют форму данных, получаемых React-компонентом.

Если нет описаний `props.*`, редактируемых полей нет. Неизвестные `@kroy`-параметры, неверные пути полей и неподдерживаемые JSDoc-типы приводят к ошибке генерации, а не молча игнорируются.

## Генерация

Команда: `yarn parts:generate`.

- `dist/kroy/parts.mjs` — полный реестр компонентов для редактора.
- `dist/kroy/parts.json` — метаданные для автоматических полей редактора.
- `yarn site:parts` создаёт `dist/kroy/site-parts.mjs` только с запчастями из `demo/page.json`.
- Файлы в `dist/` не правятся вручную и не считаются исходным кодом проекта.

Устаревшие `fields` внутри `package.json` отдельных запчастей, которые ещё встречаются в репозитории, **не участвуют** в формировании метаданных. Источник истины — JSDoc.

## Известные ограничения прототипа

- JSDoc ищется непосредственно перед `export default`; отдельное объявление функции с последующим `export default Name` не анализируется автоматически.
- Поддержан ограниченный набор простых типов и массивов объектов. Произвольные вложенные типы и JSDoc-пути вида `props.a.b` пока не поддерживаются.
- `required` и некоторые `validators` уже присутствуют в метаданных, но полноценная проверка при серверном сохранении ещё не реализована.
- Проверка удалённых/переименованных запчастей и миграции данных страниц отложены.

Имена запчастей используются в документах страниц, поэтому переименование требует осознанного обновления этих документов.
