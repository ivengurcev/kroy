# Архитектура Kroy / Oysite

Принятые решения и состояние исходников на 1 ноября 2026 года. Требования и
их статусы — в [requirements.md](requirements.md), обязательные ограничения —
в [arch-rules.md](arch-rules.md). Этот документ не является инструкцией деплоя.

## Компоненты и границы

| Компонент | Ответственность |
|---|---|
| Vyaz (`vyaz/`, локальный `@vyaz/core`) | Hono-сервер, маршруты, SSR и гидратация админки, интеграция Auth.js, esbuild |
| Kroy (`server.mjs`, `api/`, `admin/`) | Конфигурация приложения, бизнес-API, права сайта и административный интерфейс |
| `site/parts/`, `site/widgets/`, `site/runtime/` | Подготовка данных, React-представления и публичный runtime |
| `site/components/`, `site/themes/`, `site/styles/` | Общие компоненты, темы и стили публичного сайта |
| `build/site/` | SSG, рендер HTML, клиентская гидратация и генерация данных страниц |
| `build/registry/` | Discovery запчастей/виджетов и генерация полных реестров |
| `build/publication/`, `build/nginx/` | Подготовка релизов, блокировка публикации, выбор активного релиза и конфигурация Nginx |
| `scripts/` | CLI-обёртки и команды сайтов, публикации, разработки и эксплуатации |
| PostgreSQL и `db/` | Данные платформы, SQL-доступ и миграции dbmate |
| Nginx Kroy | Статика релизов, HTTP-правила URL, прокси приложения |
| Системный Nginx в production | Внешний reverse proxy и HTTPS |

Проект использует JavaScript, React 19, esbuild и Yarn 4 PnP; Vyaz подключён
через `portal:./vyaz`. Kroy использует сервер Vyaz, а публичный SSG работает
отдельно от SSR на HTTP-запросах. Это сохраняет общую инфраструктуру админки и
позволяет отдавать публичные страницы без серверного React-рендеринга на каждый запрос.

## Домены, пользователи и доступ

`domains.hostname` связывает точный hostname с сайтом. `api/getHostname.mjs`
нормализует `Host`; порт и завершающая точка не участвуют в поиске. `slug` сайта
используется в CLI и каталогах, не вычисляется из домена. Исходный Host сохраняется
при проксировании. Клиентский `X-Forwarded-Host` не выбирает tenant.

Auth.js подключён через Vyaz (`@hono/auth-js`, Credentials provider). Kroy задаёт
проверку email/пароля и JWT-сессию в `auth.mjs`. Пароль хранится как scrypt-хеш;
нужен `AUTH_SECRET`. Страница входа `/auth/signin` собственная, выход —
`/auth/signout`. Cookies используются на домене входа, единого междоменного SSO нет.

`hasAccess` повторно читает активного пользователя из БД. Superadmin проходит
проверку доступа, обычному пользователю нужна `site_memberships.role = admin`
для сайта текущего Host. Затем обработчики ограничивают данные текущим сайтом,
в том числе для superadmin. Общий допуск роли `admin` прост, но не реализует
исходное разделение структурных прав и редактирования содержимого владельцем —
это [открытое продуктовое решение](requirements.md#границы-mvp-и-открытые-решения).

Административный интерфейс находится в `admin/`; `server.mjs` подключает его страницы и
HTML/auth layouts. API страниц, настроек, каталога, модерации, статей, предпросмотра и
публикации приватны. Публичны чтение медиа своего сайта, отправка отзыва,
готовность оплаты и старт checkout. Точные маршруты — в [ROUTING.md](ROUTING.md).
Центральная панель пока не реализована; сайты, домены и доступ назначаются CLI.

## Данные

PostgreSQL хранит `sites`, `domains`, `pages`, `redirects`, `users`,
`site_memberships`, `media`, `product_categories`, `products`, `reviews`,
`articles`, `site_payment_integrations`. Схема — [db/schema.sql](../db/schema.sql),
изменения — [SQL-миграции](../db/migrations). Наличие миграции и schema snapshot
не доказывает её применение на конкретном сервере.

Страница — упорядоченный JSONB-массив блоков с обязательным `view`, отдельно от
названия, адреса, типа страницы и признака удаления. Редактор сохраняет документ
целиком. Сервер проверяет форму, известные имена и совместимость контрактов,
но не выполняет полную валидацию всех props по JSDoc. Метаданные остаются в коде.

Пути обычных страниц уникальны внутри сайта, включая корзину. `redirects`
ссылается на UUID страницы, поэтому прежние URL ведут сразу на её текущий путь.
Составные ключи ограничивают межсайтовые связи redirects и детальных шаблонов.
Принадлежность медиа и записей также проверяется прикладным кодом; одна ссылка
по UUID не заменяет проверки сайта. Медиа хранятся файлами в `data/media`, БД
хранит принадлежность и метаданные. Загрузка изображений использует Sharp/WebP.

## Запчасти, виджеты и редактор

Запчасть синхронно преобразует настройки блока, контекст, текущую запись и общие
данные сайта. Виджет получает `{ data, options, context }` и возвращает React-разметку.
Именованный контракт связывает совместимые модули; JSDoc задаёт поля и обязательный
виджет по умолчанию. Это позволяет менять отображение без дублирования выборок.
Точная форма данных, регистрация и миграция старого контента — в [PARTS.md](PARTS.md).

Редактор использует полные реестры, SSG — только модули используемых блоков и
виджетов. Общий `Page` вызывает подготовку и отображение в обеих средах.
Редактор добавляет временные id, но сохраняет только публичный контракт блока.
Живое редактирование и приватный предпросмотр сохранённого сайта используют
те же компоненты; предпросмотр не переключает публичный релиз. Подробнее —
[EDITOR.md](EDITOR.md).

## Статическая сборка и навигация

`scripts/buildSite.mjs` запускает реализацию `build/site/buildSite.mjs`: она читает
сохранённые данные, разворачивает статьи по шаблонам, создаёт сокращённые реестры
и генерирует HTML через React DOM Server, затем общий app.js,
app.css и ресурсы через esbuild. Временный staging заменяет предыдущий только
после успеха. Каталог действующего релиза при сборке не меняется.

Данные сайта, обычных страниц, шаблонов и статей читаются в REPEATABLE READ;
каталог и отзывы сейчас загружаются отдельными запросами после этой транзакции.
Поэтому сборка не гарантирует единый транзакционный снимок всех подсистем.

Основное содержимое и `<title>` уже находятся в HTML. Отдельные SEO-поля,
canonical, OG/Twitter, sitemap и robots пока отсутствуют: принятые требования
сохранены в [requirements.md](requirements.md#поиск-и-публичные-адреса).

SSR и клиент используют одни реестры и настройки CSS Modules. `build/site/hydrateSite.jsx`
гидрирует `site/runtime/SiteApp.jsx`; общие стили и импортированные изображения/шрифты собираются
esbuild. Для обычных известных страниц `SiteApp` использует встроенный реестр и
History API без запроса новых данных. Неизвестные клиентскому реестру URL
открываются обычным HTTP-переходом. Это относится и к детальным страницам статей:
их полные записи находятся только в JSON payload соответствующего HTML,
а не в общем bundle. Массовая загрузка всех текстов статей исключена ценой
полного перехода между деталями. Разделение JS на чанки пока не реализовано.

## Публикация и HTTP-семантика

Сохранение меняет БД. `scripts/publishSite.mjs` берёт общий PostgreSQL advisory lock,
запускает сборку и передаёт подготовленный staging в
`build/publication/publishPreparedSite.mjs`. Он создаёт неизменяемый релиз,
подставляет release-id в URL ресурсов, вызывает генератор
`build/nginx/generateNginxConfig.mjs`, проверяет конфигурацию и выполняет reload.
CLI, административный API и удалённый deploy вызывают этот общий процесс.
Откат использует ту же блокировку.

Сейчас сохраняются пять последних релизов; активный определяется конфигурацией
Nginx, не порядком каталогов. Старые ресурсы остаются доступны в пределах
сохранённых релизов. Ошибка переключения запускает восстановление прежней
конфигурации; сбой восстановления сообщается отдельно, релиз остаётся для диагностики.
Rollback переключает файлы и правила, но не возвращает БД к прежнему содержимому.

Административный API хранит статус фоновой публикации в памяти процесса; это
не долговечная очередь и не журнал задач. Прямые `site:build` используют общие
промежуточные модули и не защищены publish-lock: параллельные standalone-сборки
нельзя считать изолированными.

Nginx возвращает готовый HTML, 301 для прежних URL обычных страниц, 410 для
удалённых и их истории, 404 для неизвестных адресов/Host. Fallback на SPA index
нет. Для конкретных адресов статей история 301/410 ещё не ведётся.

## Темы и динамические функции

Темы — JSON-файлы в `site/themes/`; сайт хранит theme id, режим и overrides.
`site/themes/themeRegistry.mjs` рассчитывает пять основных цветов каждой палитры, общие
токены типографики/геометрии и производные значения. `site/runtime/SiteRoot.jsx` применяет
`--site-*` только к публичному поддереву; `AdminTheme` независим.
В режиме system SSR и первый клиентский render светлые, предпочтение устройства
применяется эффектом после гидратации. Это сохраняет начальную разметку согласованной.

Отзывы живут отдельно от страниц со статусами pending/published/rejected.
Публичный POST поддерживает фото, honeypot и ограничение частоты в памяти процесса;
последнее не является распределённой защитой. Модерация приватна. На статический
сайт попадает снимок опубликованных отзывов, новые изменения требуют публикации.

Статьи хранят Lexical JSON и состояния draft/published. Модель страниц поддерживает
standard/list/detail, источники articles/products/reviews и один detail-шаблон
на список, включая шаблон в корзине. Сборка разворачивает только статьи: опубликованная
запись + шаблон дают конкретный URL, `record` и `context.params`. Список получает
краткие данные и связанный шаблон. Read-only renderer выводит поддерживаемые
узлы React-компонентами и ограничивает схемы ссылок. Это генерация во время
публикации, а не динамический SSR деталей на каждый запрос.

## Платежи

`site_payment_integrations` хранит настройки по сайту и провайдеру; частичный
уникальный индекс допускает одну активную систему. Изменение настроек/активации
сериализуется блокировкой сайта. Сейчас реестр содержит только Prodamus.

Браузер после гидратации проверяет готовность, отправляет только productId.
Сервер повторно читает опубликованную позицию своего сайта, цену, тип и активную
интеграцию, подписывает запрос HMAC-SHA256 и получает у Prodamus готовую ссылку.
Это исключает доверие к цене статического снимка или данным покупателя в браузере.
Ключ не экспортируется, `PRODAMUS_SYS` задаётся окружением платформы. Покупатели,
заказы, webhook и история оплат не хранятся. Контракты и настройка —
[prodamus.md](prodamus.md).

## Среды и артефакты

Development: Compose с PostgreSQL 16, app и Nginx; на хост опубликован только
127.0.0.1:8080. Управление Nginx — внутренний HTTP-адаптер validate/reload,
без Docker socket. Production: системные PostgreSQL и Node.js, Yarn PnP,
systemd, отдельный Nginx Kroy и внешний системный Nginx с TLS.
Ansible содержит bootstrap, provision/deploy и отдельный выпуск сертификата
oysite.ru / *.oysite.ru через Certbot/acme-dns. Автоматическое TLS-подключение
произвольного клиентского домена не реализовано.

| Каталог | Назначение |
|---|---|
| `dist/public/`, `dist/ssr/` | Клиентская и SSR-сборки Vyaz |
| `dist/kroy/` | Метаданные, общие промежуточные модули и staging/<slug> |
| `dist/sites/<slug>/<release-id>/` | Опубликованные неизменяемые релизы |
| `dist/kroy/nginx-dev/` | Конфигурация и runtime Nginx Compose |
| `dist/kroy/nginx/` | Конфигурация и runtime standalone/production Nginx по умолчанию |
| `data/media/` | Загруженные медиа |

Команды, перенос данных, диагностика и сохранённые инструкции standalone —
[infra/README.md](../infra/README.md); VPS, systemd и TLS —
[infra/ansible/README.md](../infra/ansible/README.md).

## Открытые решения и известные пробелы

Продуктовые разногласия (права владельца, SEO перед запуском, история URL статей,
собственные домены) перечислены только в [requirements.md](requirements.md#границы-mvp-и-открытые-решения).
Не следует превращать текущие ограничения снимков, параллельных сборок или
in-memory статусов в обязательные архитектурные решения.

Есть техническое несоответствие резервирования путей: `api/pageFields.mjs`
запрещает первые сегменты admin/api/public/static/uploads, но Nginx дополнительно
перехватывает auth и /_kroy/releases, а клиентский runtime исключает assets.
Валидация не полностью отражает пространства инфраструктуры. В рамках аудита
код не исправляется; новое правило совместимости этих путей не выдумывается.
