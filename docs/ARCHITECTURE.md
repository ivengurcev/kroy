# Архитектура платформы и публикации

**Статус:** согласованная целевая архитектура, **не текущая реализация**. В прототипе пока есть редактор и генерация полного реестра; PostgreSQL, мультисайтовый сервер, домены, Caddy и публикация не подключены.

Сфера продукта и ограничения MVP: [PRODUCT](PRODUCT.md). Контракт запчастей: [PARTS](PARTS.md).

## Границы компонентов

- **Kroy** — бизнес-логика управления сайтами, пользователями, страницами, запчастями, медиа, отзывами и публикацией.
- **Vyaz** ([репозиторий](https://github.com/ivengurcev/vyaz)) — общие механизмы React-приложения: маршруты, серверный рендеринг, сборка, API/авторизация. Kroy предполагается построить *на* Vyaz, не встраивая предметную логику конструктора в ядро.
- **Hono API** — единый сервер платформы и динамических функций сайтов.
- **PostgreSQL** — данные сайтов, страниц, пользователей и отзывов.
- **Caddy** — кандидат для раздачи статических файлов, проксирования `/api/*` и автоматического HTTPS. Решено проверить экспериментально; конфигурация и деплой ещё не утверждены.

Концептуально:

~~~text
Редактор Kroy ────────────────> Hono API ─────> PostgreSQL
                                      │
                         сохранение / публикация
                                      │
                               статические сайты
                                      │
Посетитель ──> Caddy ────────────────┤
                  └── /api/* ────────> Hono API
~~~

## Модель содержимого

Каждая страница хранит порядок и свойства запчастей как **один JSONB-документ** (массив объектов):

~~~json
[
  {
    "part": "@kroy/hero",
    "props": {
      "title": "Заголовок",
      "description": "Описание"
    }
  },
  {
    "part": "@kroy/contacts",
    "props": {
      "phone": "+7 999 123-45-67",
      "socials": []
    }
  }
]
~~~

- Не хранить `id` экземпляров ради React, внутренние UI-состояния и настройки редактора в документе страницы.
- Имена запчастей — устойчивые ссылки на код. Метаданные и схемы полей определяются **в JS/JSDoc**, не дублируются в БД.
- Загрузка и сохранение страницы — операция над документом целиком. Сохранение/публикация атомарны; отдельные черновики в MVP не нужны.
- При подключении сервера потребуется проверка ссылок на запчасти и допустимых `props`. Конкретная модель версий и конфликтов редактирования ещё не утверждена.
- Отзывы хранятся отдельно, поскольку у них свой жизненный цикл модерации.

Конкретная SQL-схема (`sites`, `domains`, `pages`, `users` и т. д.), связи и миграции **пока не зафиксированы**.

## Мультисайтовость и домены

Одна инсталляция обслуживает несколько сайтов. Сайту сопоставляются один или несколько доменов. Предусмотрены технические поддомены платформы и собственные домены клиентов.

- Публичный статический сервер должен выдавать файлы **нужного сайта** по запрошенному домену.
- `/api/*` проксируется на общий Hono backend; backend определяет сайт по **проверенному исходному хосту** запроса и сопоставлению домена в БД.
- Нельзя доверять произвольно присланным клиентом `Host` или `X-Forwarded-Host`: правила доверия между Caddy и Hono нужно определить при реализации.
- Для технических доменов можно использовать wildcard DNS/TLS, для клиентских нужен автоматический HTTPS; вариант Caddy On-Demand TLS требует контроля разрешённых доменов, чтобы не выдавать сертификаты для посторонних хостов.

Ранее обсуждённый порядок проверки Caddy: локальная отдача сайта и прокси → технические домены → клиентские домены с On-Demand TLS → автоматизация. Пока это план эксперимента, а не рабочая инфраструктура.

## Публичная сборка

Цель — **преимущественно статический HTML**, доступный без запуска React в браузере.

1. Сборщик получает опубликованные документы страниц конкретного сайта.
2. Вычисляет **уникальные имена используемых запчастей**.
3. Подключает только их, а не полный каталог `parts/`.
4. Генерирует HTML средствами серверного React-рендеринга и необходимые статические ресурсы.
5. Клиентский JavaScript нужен лишь для интерактивных запчастей. Для него предусматриваются динамические импорты и разделение на чанки; статические запчасти не требуют обязательной гидратации.

Важно различать:
- **не включать неиспользуемые запчасти в публичную сборку вообще**;
- **не загружать JavaScript нужной запчасти, пока он не требуется в браузере**.

Редактор передаёт в `Page` полный реестр `generated/parts.mjs`. Будущая публичная сборка должна передавать только используемые запчасти; формирование такого реестра ещё не реализовано.

Детали интерактивной гидратации, маршрутизации опубликованных сайтов, ассетов и инкрементальных пересборок пока не утверждены.

## Не проектировать преждевременно

- Автономные архивы и перенос сайта на отдельный сервер.
- Отдельный single-site runtime.
- Универсальную систему версионирования и публикационных стадий.
- Сложную систему тем/медиа и инфраструктуру из множества микросервисов.

Сначала проверяются отдельные вертикальные срезы: редактор → чистый JSON → сборка используемых запчастей → статический сайт → затем хранение и публикация.
