**Статус:** согласованная целевая архитектура. Не все описанные компоненты реализованы.

Текущее состояние проекта описано в [README](../README.md).

## 1. Общая концепция

Kroy — единая мультисайтовая платформа для создания и обслуживания небольших клиентских сайтов.

Сайты собираются из переиспользуемых React-компонентов — **запчастей** (*parts*).

Платформа отвечает за:

- Управление сайтами и их содержимым.
- Визуальный редактор страниц.
- Управление пользователями и правами доступа.
- Хранение данных.
- Генерацию и публикацию сайтов.
- Общий API для динамических функций.
- SEO и социальные метаданные публичных страниц.

Публичные сайты преимущественно статические. Их работа не должна зависеть от постоянного серверного рендеринга React.

## 2. Разделение ответственности

Архитектура состоит из нескольких самостоятельных частей.

| Компонент | Ответственность |
|---|---|
| **Vyaz** | Инфраструктура основного приложения: Hono, маршрутизация, SSR, авторизация, сборка |
| **Kroy** | Предметная логика конструктора сайтов |
| **Сборщик Kroy** | Генерация публичных HTML-страниц и ресурсов |
| **PostgreSQL** | Хранение сайтов, доменов, страниц, пользователей и других данных |
| **Caddy** | Раздача статических сайтов, домены, HTTPS, перенаправления и проксирование API |

### 2.1. Vyaz

[Vyaz](https://github.com/ivengurcev/vyaz) — собственный React-фреймворк на базе Hono и esbuild.

**Kroy является приложением на Vyaz, а не расширением самого фреймворка.**

Vyaz предоставляет:

- HTTP-сервер на Hono.
- Серверную маршрутизацию.
- Серверный рендеринг React (SSR).
- Клиентскую маршрутизацию.
- Сборку клиентского и серверного JavaScript.
- Механизмы авторизации и контроля доступа.
- Инфраструктуру API.

Эти возможности используются для редактора, административного интерфейса и серверной части платформы.

Vyaz не должен содержать специфичную для Kroy логику сайтов, запчастей, страниц или публикации.

### 2.2. Kroy

В Kroy остаются:

- Обнаружение и регистрация запчастей.
- Обработка JSDoc и метаданных редактора.
- Редактирование структуры и содержимого страниц.
- Управление сайтами, доменами и пользователями.
- Проверка и сохранение данных.
- Управление публикацией.
- Управление публичными URL, перенаправлениями и SEO.
- Обработка отзывов и других динамических функций.

Kroy использует инфраструктуру Vyaz, но самостоятельно определяет модели данных, правила доступа и бизнес-логику.

**Отдельный Hono-сервер внутри Kroy не создаётся.** Используется серверная инфраструктура Vyaz.

### 2.3. Сборщик публичных сайтов

Сборщик Kroy — отдельная подсистема.

Его задача:

1. Получить данные страниц.
2. Определить необходимые запчасти.
3. Подготовить реестр используемых React-компонентов.
4. Сгенерировать HTML, включая SEO-метаданные.
5. Собрать необходимые статические ресурсы.
6. Подготовить sitemap, robots и правила перенаправлений.
7. Подготовить результат к публикации.

Для генерации HTML используется серверный React-рендеринг.

**Сборщик не обязан использовать существующий механизм SSR Vyaz.**

SSR Vyaz ориентирован на обработку HTTP-запросов. Сборщик Kroy решает другую задачу — генерацию готовых файлов.

Если в дальнейшем обнаружится повторяющаяся инфраструктурная логика, её можно будет выделить в Vyaz. Пока специально объединять эти механизмы не требуется.

## 3. Текущее состояние и следующие этапы

### Реализовано

- Kroy подключён к локальному пакету `@vyaz/core` через Yarn PnP.
- Vyaz собирает SSR- и клиентскую части административного интерфейса.
- PostgreSQL запущен через Docker Compose.
- Миграциями dbmate созданы таблицы `sites`, `pages`, `domains` и `redirects`.
- Каждый сайт может быть связан с несколькими доменами.
- API определяет сайт по HTTP-заголовку `Host` и таблице `domains`.
- Доступ к страницам ограничивается принадлежностью текущему домену.
- Реализованы получение, создание и сохранение страниц, а также получение их списка.
- Редактор загружает страницу из PostgreSQL и сохраняет изменения через API.
- Редактор использует полный реестр запчастей и формирует документ `{ part, props }`.
- Реализованы список страниц `/admin/pages` и редактор `/admin/pages/:pageId/edit`.
- Текущий маршрут `/admin` открывает редактор главной страницы.
- Для каждого собираемого сайта формируется реестр используемых запчастей без неиспользуемых компонентов.
- Активные страницы сайта загружаются из PostgreSQL и генерируются средствами React DOM Server как отдельные HTML-файлы.
- Локальный Caddy раздаёт собранные сайты, применяет подготовленные правила `301`/`410` и возвращает `404` для неизвестных URL и доменов.
- Текущие публичные страницы отображаются без клиентского JavaScript; публичная гидратация и SPA-навигация ещё не реализованы.

Результаты сборки разделены по назначению:

| Путь | Содержимое |
|---|---|
| `dist/public/` | Клиентская сборка Vyaz |
| `dist/ssr/` | Серверная сборка Vyaz |
| `dist/kroy/` | Реестры, метаданные и промежуточные файлы Kroy |
| `dist/sites/<site>/` | Готовые статические сайты |

### Ещё не реализовано

- Публичная React-гидратация, интерактивные запчасти и SPA-навигация.
- Сборка CSS, клиентского JavaScript и статических данных для переходов между страницами.
- Атомарная production-публикация HTML, ресурсов, данных страниц и правил маршрутизации.
- Production-конфигурация Caddy и HTTPS.
- SEO-настройки страниц и сайтов.
- Пользователи, авторизация и разграничение доступа.
- Центральная панель управления всеми сайтами.
- Динамические функции публичных сайтов.

## 4. Модель содержимого страниц

Каждая страница хранится в PostgreSQL как один JSONB-документ.

Документ представляет собой упорядоченный массив запчастей:

```json
[
  {
    "part": "@kroy/hero",
    "props": {
      "title": "Заголовок",
      "description": "Описание"
    }
  },
  {
    "part": "@kroy/contacts",
    "props": {
      "phone": "+7 999 123-45-67",
      "socials": []
    }
  }
]
```

Принципы:

- Документ содержит только `part` и `props`.
- Служебные идентификаторы React и состояние редактора не сохраняются.
- Порядок массива определяет порядок запчастей на странице.
- Одна запчасть может встречаться несколько раз.
- Имена запчастей служат устойчивыми ссылками на компоненты.

Метаданные запчастей определяются исходным кодом и JSDoc. Дублировать их в базе данных не требуется.

Загрузка и сохранение страницы выполняются над документом целиком.

Для MVP отдельная система черновиков не предусматривается: сохранённое содержимое становится источником следующей публичной сборки. Сейчас обновление готовых файлов запускается отдельной командой; автоматическая и атомарная публикация будет реализована позже.

Сервер уже проверяет структуру документа и существование запчастей. Полноценная проверка допустимости свойств по их метаданным остаётся дальнейшей задачей.

### 4.1. Модель PostgreSQL

Минимальная реализованная схема:

**sites**

- `id` — UUID сайта.
- `slug` — уникальный технический идентификатор.
- `name` — отображаемое название.

**pages**

- `id` — UUID страницы.
- `site_id` — ссылка на сайт.
- `path` — публичный путь относительно корня домена.
- `title` — название страницы.
- `content` — JSONB-документ.
- `deleted_at` — дата мягкого удаления или `NULL` для активной страницы.

Ограничение `UNIQUE(site_id, path)` не допускает повторения публичных путей внутри одного сайта.

**domains**

- `id` — UUID записи.
- `site_id` — ссылка на сайт.
- `hostname` — уникальное доменное имя.

Один сайт может иметь несколько доменов. Домен не является частью документа страницы.

**redirects**

- `site_id` — сайт, внутри которого зарезервирован прежний путь.
- `from_path` — прежний публичный путь страницы.
- `page_id` — ссылка на текущую страницу; актуальный адрес берётся из `pages.path`.

`UNIQUE(site_id, from_path)` не позволяет двум страницам резервировать один прежний адрес. Составной внешний ключ `(site_id, page_id)` гарантирует, что редирект и целевая страница принадлежат одному сайту. При повторных переименованиях каждый прежний путь ссылается непосредственно на UUID страницы, поэтому цепочки редиректов не создаются.

Мягкое удаление страницы сохраняет её редиректы. Статическая сборка помещает прежние и текущий адреса удалённой страницы в список `gone`; локальный Caddy уже применяет эти правила как `410 Gone`. Production-публикация правил пока не реализована.

Дополнительные поля и таблицы для SEO, пользователей и других функций будут добавляться миграциями по мере реализации.

## 5. Редактор

Редактор — React-приложение внутри Vyaz. Он серверно рендерится и гидратируется в браузере.

Основные маршруты:

| URL | Назначение |
|---|---|
| `/admin` | Редактор главной страницы |
| `/admin/pages` | Список страниц сайта |
| `/admin/pages/:pageId/edit` | Редактор выбранной страницы |

Редактор использует полный реестр доступных запчастей.

Он отвечает за:

- Управление структурой страницы.
- Настройку свойств запчастей.
- Предварительный просмотр.
- Загрузку и сохранение содержимого через API.

Запчасти остаются обычными React-компонентами. Для отображения редактор использует тот же формат `part` и `props`, что и публичный сайт.

Внутренние идентификаторы экземпляров используются только в состоянии редактора и не попадают в документ страницы.

### 5.1. API страниц

Согласован единый доменно-зависимый API:

```text
GET  /api/pages
POST /api/pages
GET  /api/pages?path=/
GET  /api/pages/:pageId
PATCH /api/pages/:pageId
PUT  /api/pages/:pageId
DELETE /api/pages/:pageId
POST /api/pages/:pageId/restore
```

Сайт определяется сервером по `Host`.

Клиент не передаёт `siteId` для операций с конкретной страницей.

При чтении используется SQL с `JOIN` между `pages` и `domains`.

Создание страницы и изменение её пути выполняются в транзакции с блокировкой строки сайта. Новый путь проверяется одновременно против `pages` и `redirects`, а прежний путь сохраняется в `redirects`.

Это обеспечивает проверку принадлежности страницы сайту непосредственно в SQL-запросе.

**Страницу можно открыть или изменить только при обращении через домен, зарегистрированный для её сайта.** Знание UUID страницы не даёт доступа к ней через другой домен.

Доменная изоляция не заменяет авторизацию пользователя. Проверка прав на изменение данных обязательна до публичного развёртывания.

### 5.2. Центральная и доменная панели

Центральная панель предназначена для управления сайтами, доступными пользователю.

Редактирование конкретного сайта выполняется на одном из его зарегистрированных доменов через `/admin`.

Центральная панель не получает исключения из правила доменной изоляции API страниц.

Компоненты редактора могут использоваться повторно. Создавать отдельную реализацию редактора для центральной панели не требуется.

Подробная схема маршрутизации описана в [ROUTING.md](ROUTING.md).

## 6. Сборка публичного сайта

### 6.1. Общий принцип

Целевая архитектура публичного сайта — **SSG + React Hydration + SPA Navigation**.

Это не классическая SPA с единственным `index.html`. Каждая публичная страница имеет собственный предварительно сгенерированный HTML-файл. Прямой HTTP-запрос не запускает серверный React-рендеринг: Caddy возвращает готовый файл соответствующего URL.

Процесс сборки:

```text
Данные сайта из PostgreSQL
            ↓
Определение используемых запчастей
            ↓
Формирование реестра сайта
            ↓
React → HTML
            ↓
SEO и социальные метаданные
            ↓
CSS, JavaScript, изображения и данные страниц
            ↓
Готовый сайт
```

Редактор использует полный реестр запчастей.

**Публичный сайт получает только необходимые компоненты.** Неиспользуемые запчасти исключаются из сборки. Все страницы одного сайта используют общий клиентский React-runtime, а не отдельное приложение для каждого URL. Клиентский код может разделяться на чанки.

Сборка должна включать готовый основной контент и SEO-метаданные в HTML, а также необходимые CSS, JavaScript, изображения и другие ресурсы.

Публичная сборка и клиентский runtime являются ответственностью Kroy. Административное приложение и API продолжают использовать инфраструктуру Vyaz; специфичная логика публичных сайтов не переносится во фреймворк.

### 6.2. JavaScript и гидратация

При прямом открытии любой публичной страницы:

1. Caddy возвращает готовый HTML этой страницы.
2. Браузер загружает необходимые CSS и JavaScript.
3. React гидрирует существующую разметку.
4. Интерактивные компоненты и клиентская навигация начинают работать.

Серверный рендеринг при сборке должен быть совместим с гидратацией. Серверная и первоначальная клиентская разметка не должны различаться. HTML должен содержать или ссылаться на данные начальной страницы, необходимые клиентскому runtime.

JavaScript расширяет готовую страницу, но не является условием доступа к основному содержимому: без его выполнения текст, ссылки и SEO-метаданные остаются в HTML.

### 6.3. SPA-навигация

После гидратации внутренние переходы выполняются без полной перезагрузки страницы. Клиент обновляет URL и историю через History API; кнопки Back и Forward должны восстанавливать соответствующую страницу.

Данные для переходов берутся из предварительно собранных статических ресурсов. Клиентская навигация не должна запускать новый серверный React-рендеринг. Конкретный формат этих данных и реализация клиентского роутера будут определены отдельной задачей.

Прямое открытие и обновление любого существующего URL по-прежнему возвращают его собственный HTML. Сервер продолжает обрабатывать постоянные перенаправления и удалённые URL как `301` и `410`, а неизвестные страницы — как `404`. Нельзя заменять публичную маршрутизацию fallback на единый `index.html`.

Клиентская навигация должна учитывать опубликованный набор маршрутов и перенаправлений, но не заменяет серверную HTTP-семантику.

### 6.4. Результат сборки

Концептуальная структура результата:

```text
dist/sites/<slug>/
├── index.html
├── services/
│   └── index.html
├── contacts/
│   └── index.html
└── assets/
    ├── app.[hash].js
    ├── app.[hash].css
    └── ...
```

Имена и разбиение файлов в `assets/` не зафиксированы этим решением.

Сейчас команда `yarn site:build <slug>` загружает из PostgreSQL все активные страницы сайта и формирует для них один `dist/kroy/site-parts.mjs`. Реестр содержит статические импорты только используемых запчастей. Каждая страница получает готовый HTML без клиентского JavaScript.

Главная страница записывается в `dist/sites/<slug>/index.html`, вложенные публичные пути — в соответствующие каталоги с `index.html`. Перед повторной сборкой очищается только каталог выбранного сайта, поэтому устаревшие файлы удалённых и переименованных страниц исчезают.

Сборка создаёт `dist/kroy/routing/<slug>.json`. Активные цели дают прямые правила `301` со старого пути на текущий, а прежние и текущие пути удалённых страниц попадают в `gone` для ответа `410`. Правила других сайтов в файл не включаются; локальный Caddy уже применяет этот файл через сгенерированную конфигурацию.

Публичная CSS/JavaScript-сборка, React-гидратация, статические данные для клиентских переходов, SPA-навигация и разделение клиентского кода пока не реализованы.

При будущей публикации HTML, CSS, JavaScript, данные страниц и правила маршрутизации должны переключаться как одна согласованная версия. Механизм атомарной публикации определяется отдельно.

## 7. Мультисайтовость

Одна инсталляция Kroy обслуживает несколько независимых сайтов.

У каждого сайта предполагаются:

- Собственные страницы и содержимое.
- Собственные настройки оформления.
- Собственные SEO-настройки.
- Один или несколько доменов.
- Назначенные пользователи.
- Собственные данные динамических функций.

При этом:

- Каталог запчастей общий.
- Серверное приложение общее.
- PostgreSQL общий.
- API общий.
- Публичные файлы каждого сайта разделены.

Отдельный режим `single-site` не предусматривается. Платформа с одним сайтом работает по тем же правилам.

## 8. Домены и веб-сервер

Для локального preview нескольких сайтов используется один Caddy. Он принимает точные hostname из таблицы `domains`, но production-конфигурация, публичный DNS и HTTPS остаются будущими задачами.

Основные задачи:

- Выдача статических файлов соответствующего сайта.
- Обслуживание технических поддоменов платформы.
- Подключение собственных доменов клиентов.
- Автоматическое управление HTTPS.
- Проксирование `/api/*` и `/admin/*` на общий backend Kroy.
- Обработка постоянных перенаправлений и удалённых URL.

Backend определяет сайт по исходному домену запроса и данным PostgreSQL.

Локальный Caddy передаёт исходный `Host` в Vyaz, а backend определяет сайт по точному соответствию таблице `domains`. Клиентский `X-Forwarded-Host` для выбора сайта не используется.

Для собственных доменов рассматривается Caddy On-Demand TLS с проверкой разрешённых доменов.

В preview Caddy получает домены из PostgreSQL, изолирует каталоги и правила сайтов, применяет `301`/`410` и проксирует `/admin`, `/api`, `/public`, `/static` и `/uploads` без изменения URI. Неизвестный Host получает `404`. HTTPS и production-публикация пока не реализованы.

## 9. Динамические функции

Публичные сайты могут содержать функции, которым требуется сервер.

Например:

- Отправка отзывов.
- Модерация отзывов.
- Обработка форм.
- Другие запросы к API.

Эти функции обслуживаются общим Hono API приложения Kroy на Vyaz.

Данные, имеющие собственный жизненный цикл, не должны храниться внутри JSON-документа страницы.

Например, отзывы хранятся отдельно со статусами:

- `pending`
- `published`
- `rejected`

Предусматривается базовая защита от спама.

Конкретные API-контракты пока не определены.

## 10. Развёртывание

Целевая инфраструктура:

- Kroy на Vyaz — серверное приложение.
- PostgreSQL — база данных.
- Caddy — веб-сервер и обратный прокси.
- Файловое хранилище — опубликованные сайты и медиа.

Для развёртывания предполагается использовать Docker Compose и постоянные тома для данных.

На этапе разработки PostgreSQL уже работает в Docker Compose, а Kroy запускается непосредственно в Linux.

Схема базы данных изменяется через SQL-миграции dbmate.

Обновление приложения, выполнение миграций и обновление PostgreSQL рассматриваются как отдельные операции.

При публикации нельзя допускать состояния, когда новый HTML уже доступен, а соответствующие правила перенаправлений ещё не обновлены, или наоборот. Механизм согласованного переключения опубликованных файлов и правил маршрутизации будет определён при реализации публикации.

## 11. SEO и социальные метаданные

**SEO является обязательной частью архитектуры публичных сайтов Kroy, а не дополнительной функцией редактора.**

Платформа должна обеспечивать корректные публичные URL, поисковые метаданные, перенаправления и предварительный просмотр ссылок в социальных сетях и мессенджерах.

Эти требования должны быть реализованы до первого публичного развёртывания сайтов.

### 11.1. Постоянство идентификаторов страниц

У каждой страницы есть постоянный UUID.

Публичный путь страницы может изменяться, но её UUID остаётся прежним.

Например:

```text
Страница: 5b3a...
Старый путь: /services
Новый путь: /our-services
```

Изменение публичного пути не должно приводить к потере истории адресов или накопленной поисковой ценности страницы.

Внутренний URL редактора, основанный на UUID, не зависит от публичного пути страницы.

### 11.2. История URL и постоянные перенаправления

При изменении публичного пути страницы Kroy должен сохранять старый адрес.

Пример:

```text
/services
    ↓ 301
/our-services
```

При обращении к старому адресу сервер должен возвращать:

```http
HTTP/1.1 301 Moved Permanently
Location: /our-services
```

Если страница переименовывается несколько раз:

```text
/services
    ↓
/our-services
    ↓
/what-we-do
```

Предыдущие адреса должны перенаправлять непосредственно на актуальный:

```text
/services      → 301 → /what-we-do
/our-services  → 301 → /what-we-do
```

**Цепочки перенаправлений необходимо исключать.**

Предпочтительно хранить историю адресов с привязкой к UUID страницы. Тогда актуальный URL можно определить по текущему состоянию страницы, а не поддерживать цепочку строковых перенаправлений.

Механизм истории адресов должен учитывать принадлежность сайту.

Точные таблицы и правила повторного использования ранее занятых URL будут спроектированы отдельно.

### 11.3. Удаление страниц

При окончательном удалении страницы без замены публичный сервер должен возвращать:

```http
HTTP/1.1 410 Gone
```

Различаем следующие ситуации:

| HTTP-код | Значение | Использование |
|---|---|---|
| `200 OK` | Страница существует | Обычная публичная страница |
| `301 Moved Permanently` | Постоянное перемещение | Страница получила новый URL |
| `302 Found` | Временное перенаправление | Временная смена адреса |
| `404 Not Found` | Страница не найдена | Неизвестный URL |
| `410 Gone` | Страница окончательно удалена | Удаление без замены |

После удаления необходимо сохранять сведения о прежних публичных URL, иначе невозможно будет отличать удалённые страницы от никогда не существовавших.

При удалении страницы с подходящей заменой в будущем предусматривается возможность указать целевую страницу и вернуть `301` вместо `410`.

Случайное удаление не должно приводить к немедленной безвозвратной потере содержимого. Конкретный механизм безопасного удаления будет определён отдельно.

### 11.4. Работа перенаправлений на статических сайтах

Публичные сайты Kroy преимущественно статические.

Поэтому перенаправления и статусы удаления должны обрабатываться на HTTP-уровне, без выполнения клиентского JavaScript.

Не использовать для постоянных перенаправлений:

- `window.location`.
- Клиентский React Router.
- HTML `meta refresh`.

При генерации и публикации сайта Kroy должен подготовить правила для Caddy или другого поддерживаемого веб-сервера.

Эти правила должны учитывать:

- Актуальные публичные пути.
- Историю перенаправлений.
- Удалённые страницы.
- Несколько доменов одного сайта.
- Отсутствие циклов и цепочек перенаправлений.

Публикация должна согласованно обновлять HTML и соответствующие правила HTTP-маршрутизации.

### 11.5. Канонические URL

Один сайт может иметь несколько доменов:

```text
vet.kroy.example
vetclinic.ru
```

Для каждого сайта необходимо предусмотреть **основной домен**.

Канонический адрес страницы формируется из основного домена и её публичного пути.

Например:

```text
https://vetclinic.ru/services
```

В HTML:

```html
<link
  rel="canonical"
  href="https://vetclinic.ru/services"
>
```

Canonical должен присутствовать непосредственно в готовом HTML.

Если один сайт доступен на нескольких доменах, необходимо избегать появления нескольких независимых индексируемых копий одного содержимого.

Для дополнительных доменов предусматриваются постоянные перенаправления на основной домен. Конкретные правила и исключения будут определены при реализации доменной конфигурации.

Смена основного домена должна корректно обновлять canonical и перенаправления.

### 11.6. Основные SEO-метаданные страницы

Для каждой публичной страницы предусматриваются:

- `title` — заголовок HTML-документа.
- `description` — описание для поисковых систем.
- `robots` — правила индексации.
- `canonical` — канонический URL.

Пример:

```html
<title>Услуги ветеринарного врача</title>

<meta
  name="description"
  content="Консультации и ветеринарная помощь."
>

<meta
  name="robots"
  content="index, follow"
>

<link
  rel="canonical"
  href="https://vetclinic.ru/services"
>
```

SEO-метаданные должны храниться отдельно от массива запчастей `content`.

Существующее поле `pages.title` используется как название страницы в административном интерфейсе. Возможность задать отдельный SEO-заголовок предусматривается при расширении модели данных.

Система должна позволять использовать общие значения сайта, когда у страницы не заданы собственные.

### 11.7. Open Graph

Для корректного предварительного просмотра ссылок в социальных сетях и мессенджерах необходимо поддерживать **Open Graph (OG)**.

Основные свойства:

| Поле | Назначение |
|---|---|
| `og:title` | Заголовок карточки |
| `og:description` | Описание карточки |
| `og:image` | Изображение карточки |
| `og:url` | Канонический адрес страницы |
| `og:type` | Тип содержимого |
| `og:site_name` | Название сайта |

Пример:

```html
<meta property="og:type" content="website">

<meta
  property="og:title"
  content="Услуги ветеринарного врача"
>

<meta
  property="og:description"
  content="Ветеринарная помощь и консультации."
>

<meta
  property="og:image"
  content="https://vetclinic.ru/media/og-services.jpg"
>

<meta
  property="og:url"
  content="https://vetclinic.ru/services"
>

<meta
  property="og:site_name"
  content="Ветеринарный врач"
>
```

OG-метаданные должны находиться непосредственно в HTML, который получает HTTP-клиент.

Нельзя рассчитывать на то, что Telegram, социальная сеть или другой потребитель ссылки выполнит JavaScript страницы.

Изображение должно быть доступно по публичному абсолютному HTTPS-адресу.

В дальнейшем могут поддерживаться дополнительные свойства, включая размеры изображения и тип содержимого.

### 11.8. Twitter Cards

Предусматривается поддержка Twitter Cards, используемых для предварительного просмотра ссылок в X и совместимых сервисах.

Основные метаданные:

```html
<meta
  name="twitter:card"
  content="summary_large_image"
>

<meta
  name="twitter:title"
  content="Услуги ветеринарного врача"
>

<meta
  name="twitter:description"
  content="Ветеринарная помощь и консультации."
>

<meta
  name="twitter:image"
  content="https://vetclinic.ru/media/og-services.jpg"
>
```

По умолчанию Twitter Cards могут использовать те же значения, что и Open Graph.

Не требуется создавать независимую систему редактирования одинаковых данных.

### 11.9. Наследование настроек

SEO и социальные метаданные должны настраиваться на двух уровнях:

1. **Сайт** — значения по умолчанию.
2. **Страница** — локальные переопределения.

Например:

```text
Настройки сайта
├── Название
├── Описание по умолчанию
├── Основное OG-изображение
├── Основной домен
└── Правила индексации

Страница /services
├── Собственный SEO title
├── Собственное description
├── Собственное OG-изображение
└── Локальные правила robots
```

При отсутствии локального значения используется подходящее значение сайта.

Точные правила наследования, включая обработку явно пустых значений, будут определены при реализации модели SEO-настроек.

Новые настройки не должны требовать внесения SEO-полей в `props` каждой запчасти.

### 11.10. Sitemap

Для каждого публичного сайта необходимо формировать `sitemap.xml`.

В sitemap должны попадать актуальные индексируемые страницы соответствующего сайта.

Не включать:

- Удалённые страницы.
- Старые URL с перенаправлением.
- Административные маршруты.
- API.
- Страницы, исключённые из индексации.

Пример:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://vetclinic.ru/</loc>
  </url>
  <url>
    <loc>https://vetclinic.ru/services</loc>
  </url>
</urlset>
```

Ссылки должны использовать канонический домен и актуальные пути.

В дальнейшем при наличии достоверных данных об изменении опубликованной страницы может добавляться `lastmod`.

### 11.11. Robots.txt

Для каждого публичного сайта предусматривается генерация `robots.txt`.

Он может содержать ссылку на sitemap и необходимые правила обхода.

Пример:

```text
User-agent: *
Disallow: /admin/
Disallow: /api/

Sitemap: https://vetclinic.ru/sitemap.xml
```

Для административных и приватных маршрутов основной защитой остаётся авторизация. `robots.txt` не является механизмом безопасности.

Для сайтов, которые ещё не готовы к публикации, необходимо предусмотреть запрет индексации. Публичные версии должны получать корректные настройки индексации при публикации.

### 11.12. Требования к HTML и HTTP

Для корректной индексации:

- Каждая публичная страница должна иметь собственный доступный URL.
- Основной контент присутствует непосредственно в HTML.
- Заголовок и метаданные присутствуют в исходном HTML.
- Страница не должна требовать JavaScript для отображения основного содержимого.
- Отсутствующие страницы получают корректный HTTP-статус.
- Постоянные перенаправления выполняются сервером.
- Изображения и другие индексируемые ресурсы доступны по корректным URL.
- Внутренние административные маршруты не должны попадать в публичную навигацию или sitemap.

Статическая генерация Kroy должна помогать выполнению этих требований без дополнительной клиентской инфраструктуры.

### 11.13. Порядок реализации SEO

SEO реализуется поэтапно, но **до первого публичного развёртывания должны работать основные механизмы**.

Приоритет:

1. Генерация публичных HTML-страниц из PostgreSQL.
2. Управление SEO-метаданными сайта и страниц.
3. История публичных URL и ответы `301`/`410`.
4. Canonical и определение основного домена.
5. Open Graph и Twitter Cards.
6. Генерация `sitemap.xml` и `robots.txt`.
7. Интеграция правил маршрутизации и перенаправлений с Caddy.

Конкретная структура дополнительных таблиц и файлов будет согласована при реализации соответствующих этапов.

Не внедрять сложную систему SEO-плагинов или универсальных правил перенаправления до появления реальных сценариев, но сохранять перечисленные требования как обязательную часть архитектуры.

## 12. За пределами MVP

В дальнейшем рассматривается экспорт отдельного сайта в автономный дистрибутив.

Он может включать:

- Используемые запчасти и их зависимости.
- Статические файлы.
- Данные сайта.
- Медиа.
- Необходимые API и серверные компоненты.
- Конфигурацию самостоятельного размещения.

При экспорте должны учитываться также публичные URL и необходимые правила перенаправлений.

Эта возможность **не входит в MVP** и не должна влиять на текущую архитектуру без реальной необходимости.

## 13. Принципы разработки

1. Реализовывать функциональность небольшими проверяемыми этапами.
2. Не добавлять абстракции ради гипотетических будущих сценариев.
3. Не дублировать инфраструктуру Vyaz внутри Kroy.
4. Не переносить бизнес-логику Kroy в Vyaz.
5. Не смешивать редактор, сборщик и публичный runtime.
6. Не сохранять в БД состояние, необходимое только интерфейсу.
7. Не отправлять клиенту JavaScript, который не нужен для работы сайта.
8. Поддерживать JavaScript без обязательного TypeScript.
9. Сохранять независимость запчастей от механизмов редактора.
10. Архитектурные решения обсуждать до реализации.
11. Не привязывать доменную маршрутизацию к особенностям локальной среды.
12. Проверять принадлежность страниц сайту на сервере.
13. Не допускать потери истории публичных URL при изменении или удалении страниц.
14. Обеспечивать корректную работу SEO без выполнения клиентского JavaScript.

**Порядок работы:** обсуждение → микрозадача Codex → проверка результата → следующая задача.

### Ближайшие технические шаги

1. Добавить SEO-метаданные и механизм обработки прежних URL.
2. Реализовать production-публикацию и конфигурацию Caddy.
3. Реализовать авторизацию и разграничение доступа до публичного развёртывания.

Публичную гидратацию и SPA-навигацию реализовывать отдельными проверяемыми этапами, не смешивая выбор клиентского роутера, формата статических данных и механизма атомарной публикации в одну задачу.
