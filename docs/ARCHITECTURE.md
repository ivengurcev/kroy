# Архитектура платформы Kroy

**Статус:** согласованная целевая архитектура. Не все описанные компоненты реализованы.

Текущее состояние проекта описано в [README](../README.md).

Смежная документация:
- [Продукт и границы MVP](PRODUCT.md)
- [Запчасти и JSDoc](PARTS.md)
- [Редактор страниц](EDITOR.md)

## 1. Общая концепция

Kroy — единая мультисайтовая платформа для создания и обслуживания небольших клиентских сайтов.

Сайты собираются из переиспользуемых React-компонентов — **запчастей** (*parts*).

Платформа отвечает за:

- Управление сайтами и их содержимым.
- Визуальный редактор страниц.
- Управление пользователями и правами доступа.
- Хранение данных.
- Генерацию и публикацию сайтов.
- Общий API для динамических функций.

Публичные сайты преимущественно статические. Их работа не должна зависеть от постоянного серверного рендеринга React.

## 2. Разделение ответственности

Архитектура состоит из нескольких самостоятельных частей.

| Компонент | Ответственность |
|---|---|
| **Vyaz** | Инфраструктура основного приложения: Hono, маршрутизация, SSR, авторизация, сборка |
| **Kroy** | Предметная логика конструктора сайтов |
| **Сборщик Kroy** | Генерация публичных HTML-страниц и ресурсов |
| **PostgreSQL** | Хранение сайтов, страниц, пользователей и других данных |
| **Caddy** | Раздача статических сайтов, домены, HTTPS и проксирование API |

### 2.1. Vyaz

[Vyaz](https://github.com/ivengurcev/vyaz) — собственный React-фреймворк на базе Hono и esbuild.

**Kroy является приложением на Vyaz, а не расширением самого фреймворка.**

Vyaz предоставляет:

- HTTP-сервер на Hono.
- Серверную маршрутизацию.
- Серверный рендеринг React (SSR).
- Клиентскую маршрутизацию.
- Сборку клиентского и серверного JavaScript.
- Механизмы авторизации и контроля доступа.
- Инфраструктуру API.

Эти возможности используются для редактора, административного интерфейса и серверной части платформы.

Vyaz не должен содержать специфичную для Kroy логику сайтов, запчастей, страниц или публикации.

### 2.2. Kroy

В Kroy остаются:

- Обнаружение и регистрация запчастей.
- Обработка JSDoc и метаданных редактора.
- Редактирование структуры и содержимого страниц.
- Управление сайтами, доменами и пользователями.
- Проверка и сохранение данных.
- Управление публикацией.
- Обработка отзывов и других динамических функций.

Kroy использует инфраструктуру Vyaz, но самостоятельно определяет модели данных, правила доступа и бизнес-логику.

**Отдельный Hono-сервер внутри Kroy не создаётся.** Используется серверная инфраструктура Vyaz.

### 2.3. Сборщик публичных сайтов

Сборщик Kroy — отдельная подсистема.

Его задача:

1. Получить данные опубликованных страниц.
2. Определить необходимые запчасти.
3. Подготовить реестр используемых React-компонентов.
4. Сгенерировать HTML.
5. Собрать необходимые статические ресурсы.
6. Подготовить результат к публикации.

Для генерации HTML используется серверный React-рендеринг.

**Сборщик не обязан использовать существующий механизм SSR Vyaz.**

SSR Vyaz ориентирован на обработку HTTP-запросов. Сборщик Kroy решает другую задачу — генерацию готовых файлов.

Если в дальнейшем обнаружится повторяющаяся инфраструктурная логика, её можно будет выделить в Vyaz. Пока специально объединять эти механизмы не требуется.

## 3. Текущее состояние и следующие этапы

### Реализовано

- Kroy подключён к локальному пакету `@vyaz/core` через Yarn PnP.
- Vyaz собирает SSR- и клиентскую части редактора и обслуживает маршрут `/`.
- Редактор использует полный реестр запчастей и формирует документ `{ part, props }`.
- Для тестовой страницы формируется отдельный реестр используемых запчастей.
- Статический demo-сайт генерируется средствами React DOM Server и отображается без клиентского JavaScript.

Результаты сборки разделены по назначению:

| Путь | Содержимое |
|---|---|
| `dist/public/` | Клиентская сборка Vyaz |
| `dist/ssr/` | Серверная сборка Vyaz |
| `dist/kroy/` | Реестры, метаданные и промежуточные файлы Kroy |
| `dist/sites/<site>/` | Готовые статические сайты |

### Ещё не реализовано

- API загрузки и сохранения страниц.
- PostgreSQL и модели данных платформы.
- Пользователи и разграничение доступа.
- Управление несколькими сайтами и доменами.
- Автоматическая публикация и конфигурация Caddy.
- Динамические функции публичных сайтов.

## 4. Модель содержимого страниц

Каждая страница хранится в PostgreSQL как один JSONB-документ.

Документ представляет собой упорядоченный массив запчастей:

```json
[
  {
    "part": "@kroy/hero",
    "props": {
      "title": "Заголовок",
      "description": "Описание"
    }
  },
  {
    "part": "@kroy/contacts",
    "props": {
      "phone": "+7 999 123-45-67",
      "socials": []
    }
  }
]
```

Принципы:

- Документ содержит только `part` и `props`.
- Служебные идентификаторы React и состояние редактора не сохраняются.
- Порядок массива определяет порядок запчастей на странице.
- Одна запчасть может встречаться несколько раз.
- Имена запчастей служат устойчивыми ссылками на компоненты.

Метаданные запчастей определяются исходным кодом и JSDoc. Дублировать их в базе данных не требуется.

Загрузка и сохранение страницы выполняются над документом целиком.

Для MVP сохранение и публикация — единая атомарная операция. Отдельная система черновиков не предусматривается.

Перед сохранением сервер должен проверять допустимость запчастей и их свойств.

Конкретная SQL-схема и механизм разрешения конфликтов одновременного редактирования пока не утверждены.

## 5. Редактор

Редактор — React-приложение внутри Vyaz. Он доступен на маршруте `/`, серверно рендерится и гидратируется в браузере.

Он использует полный реестр доступных запчастей.

Редактор отвечает за:

- Управление структурой страницы.
- Настройку свойств запчастей.
- Предварительный просмотр.
- Подготовку данных для сохранения.

Редактор не отвечает за генерацию публичных сайтов и работу с доменами.

Запчасти остаются обычными React-компонентами. Для отображения редактор использует тот же формат `part` и `props`, что и публичный сайт.

Внутренние идентификаторы экземпляров используются только в состоянии редактора и не попадают в документ страницы.

## 6. Сборка публичного сайта

### 6.1. Общий принцип

Публичный сайт должен работать преимущественно как набор статических файлов.

Процесс сборки:

```text
Данные страниц
      ↓
Определение используемых запчастей
      ↓
Формирование реестра сайта
      ↓
React → HTML
      ↓
Статические ресурсы
      ↓
Готовый сайт
```

Редактор использует полный реестр запчастей.

**Публичный сайт получает только необходимые компоненты.**

Запчасти, не используемые сайтом, не должны попадать в его сборку.

### 6.2. JavaScript и гидратация

Готовая HTML-страница должна отображаться без загрузки клиентского JavaScript.

Статические запчасти не требуют обязательной гидратации.

Для интерактивных запчастей предусматривается клиентский JavaScript с динамическими импортами и разделением кода.

Необходимо различать:

1. Исключение неиспользуемых запчастей из сборки.
2. Ленивую загрузку JavaScript используемых запчастей.

Это самостоятельные механизмы.

### 6.3. Реестр для многостраничного сайта

В будущем формируется **один реестр на весь сайт**.

Согласована следующая стратегия:

- Запчасти главной страницы импортируются статически.
- Запчасти, встречающиеся только на внутренних страницах, подключаются динамическими импортами.
- Повторно используемые запчасти не должны загружаться как отдельные дубликаты.
- Все страницы получают готовый HTML независимо от стратегии загрузки JavaScript.

**Сейчас эта оптимизация не реализуется.**

Пока у Kroy одна тестовая страница, необходимо проверить только формирование реестра её запчастей и генерацию HTML.

К многостраничной стратегии вернёмся после появления нескольких страниц.

## 7. Мультисайтовость

Одна инсталляция Kroy обслуживает несколько независимых сайтов.

У каждого сайта предполагаются:

- Собственные страницы и содержимое.
- Собственные настройки оформления.
- Один или несколько доменов.
- Назначенные пользователи.
- Собственные данные динамических функций.

При этом:

- Каталог запчастей общий.
- Серверное приложение общее.
- PostgreSQL общий.
- API общий.
- Публичные файлы каждого сайта разделены.

Отдельный режим `single-site` не предусматривается. Платформа с одним сайтом работает по тем же правилам.

## 8. Домены и веб-сервер

Для обслуживания сайтов планируется проверить Caddy.

Основные задачи:

- Выдача статических файлов соответствующего сайта.
- Обслуживание технических поддоменов платформы.
- Подключение собственных доменов клиентов.
- Автоматическое управление HTTPS.
- Проксирование `/api/*` на общий backend Kroy.

Backend определяет сайт по проверенному исходному домену запроса и данным PostgreSQL.

Нельзя доверять произвольным клиентским значениям `Host` и `X-Forwarded-Host`. Правила передачи исходного домена между Caddy и Hono необходимо определить при реализации.

Для собственных доменов рассматривается Caddy On-Demand TLS с проверкой разрешённых доменов.

Caddy пока не интегрирован; окончательная конфигурация будет определена после эксперимента.

## 9. Динамические функции

Публичные сайты могут содержать функции, которым требуется сервер.

Например:

- Отправка отзывов.
- Модерация отзывов.
- Обработка форм.
- Другие запросы к API.

Эти функции обслуживаются общим Hono API приложения Kroy на Vyaz.

Данные, имеющие собственный жизненный цикл, не должны храниться внутри JSON-документа страницы.

Например, отзывы хранятся отдельно со статусами:

- `pending`
- `published`
- `rejected`

Предусматривается базовая защита от спама.

Конкретные API-контракты пока не определены.

## 10. Развёртывание

Целевая инфраструктура:

- Kroy на Vyaz — серверное приложение.
- PostgreSQL — база данных.
- Caddy — веб-сервер и обратный прокси.
- Файловое хранилище — опубликованные сайты и медиа.

Для развёртывания предполагается использовать Docker Compose и постоянные тома для данных.

На текущем этапе настройка инфраструктуры не требуется.

## 11. За пределами MVP

В дальнейшем рассматривается экспорт отдельного сайта в автономный дистрибутив.

Он может включать:

- Используемые запчасти и их зависимости.
- Статические файлы.
- Данные сайта.
- Медиа.
- Необходимые API и серверные компоненты.
- Конфигурацию самостоятельного размещения.

Эта возможность **не входит в MVP** и не должна влиять на текущую архитектуру без реальной необходимости.

## 12. Принципы разработки

1. Реализовывать функциональность небольшими проверяемыми этапами.
2. Не добавлять абстракции ради гипотетических будущих сценариев.
3. Не дублировать инфраструктуру Vyaz внутри Kroy.
4. Не переносить бизнес-логику Kroy в Vyaz.
5. Не смешивать редактор, сборщик и публичный runtime.
6. Не сохранять в БД состояние, необходимое только интерфейсу.
7. Не отправлять клиенту JavaScript, который не нужен для работы сайта.
8. Поддерживать JavaScript без обязательного TypeScript.
9. Сохранять независимость запчастей от механизмов редактора.
10. Архитектурные решения обсуждать до реализации.

**Порядок работы:** обсуждение → микрозадача Codex → проверка результата → следующая задача.

### Ближайшие технические шаги

1. Спроектировать сохранение и загрузку документов страниц через API.
2. Зафиксировать минимальную модель сайтов, страниц и пользователей в PostgreSQL.
3. Подключить роли администратора платформы и владельца сайта.
4. Проверить публикацию одного сайта из сохранённых данных.

До появления этих вертикальных срезов не усложнять систему многостраничной динамической гидратацией, версиями документов и универсальными публикационными процессами.
