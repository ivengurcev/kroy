# Архитектурные правила

Обязательные ограничения для изменений Kroy. Бизнес-поведение и нерешённые
вопросы — в [requirements.md](requirements.md), устройство и ограничения
реализации — в [architecture.md](architecture.md).

1. **Изоляция сайта на сервере.** Доменная панель и API работают только с сайтом,
   найденным по нормализованному `Host` в `domains`. Не выбирать сайт по slug
   поддомена, клиентскому `siteId` или `X-Forwarded-Host`. Проверять принадлежность
   каждой читаемой и изменяемой записи; UUID сам по себе не даёт доступа.
2. **Авторизация отдельно от домена.** Приватные маршруты требуют активного
   пользователя и серверной проверки доступа. Скрытие кнопки не является проверкой
   прав. Публичные API допускают только явно предусмотренные публичные операции.
3. **Граница Vyaz / Kroy.** Hono, SSR административного приложения, Auth.js,
   маршрутизация и сборочная инфраструктура приложения предоставляются Vyaz.
   Модели сайтов, права на сайт, блоки, публичный runtime и публикация принадлежат
   Kroy. Не создавать второй Hono-сервер и не переносить предметную логику во Vyaz.
4. **Данные и отображение.** Запчасть — синхронная функция подготовки данных;
   React-виджет получает результат и отображает его. Выборки, фильтрация и подбор
   записей остаются в запчасти, настройки отображения — в виджете. Полный контракт
   описан в [PARTS.md](PARTS.md).
5. **Документ страницы.** Каждый блок хранится строго как
   `{ part, props, view: { name, props } }`. `view` обязателен; запчасть и виджет
   объявляют один непустой точно совпадающий контракт. Runtime fallback старого
   формата не добавлять. Совместимость проверяется сервером и сборщиком.
6. **Состояние редактора.** Временные `id`, выделение, состояния загрузки,
   предпросмотровые записи и подготовленные данные не сохраняются в `content`.
   JSDoc исходников определяет метаданные; не дублировать схему полей в БД.
   Отзывы, материалы и каталог с собственным жизненным циклом хранить отдельно.
7. **Готовый HTML и гидратация.** Каждый публичный URL имеет собственный HTML
   с основным содержимым без JavaScript. SSR при сборке и первая клиентская
   отрисовка используют одинаковые данные, виджеты, тему и CSS Modules.
   Клиентские эффекты запускаются после гидратации. Административная тема
   отделена от темы публичного поддерева.
8. **URL и публикация.** Сохранять UUID, историю адресов обычных страниц,
   доменную изоляцию и HTTP-семантику 301/410/404. Не вводить fallback неизвестных
   URL на общий index.html. Сохранение в БД не равно публикации. Публикация
   согласованно переключает HTML, данные, ресурсы и правила URL; ошибка требует
   восстановления прежней конфигурации либо явного сообщения о сбое восстановления.
9. **Публичная сборка.** Включать только используемые запчасти/виджеты и публичные
   данные. Не включать черновики материалов, скрытые позиции, приватные настройки
    и секреты. Основной контент и SEO-метаданные не зависят от клиентского JS.
10. **Платежи на сервере.** Название, цена, тип, принадлежность и доступность
    позиции определяются по БД. Клиент передаёт только идентификатор позиции.
    Ключ продавца и подпись запроса не выдаются браузеру и не попадают в сборку
    или логи. Ключ продавца шифруется на сервере. `PRODAMUS_SYS` — необязательная
    переменная платформы, не настройка сайта. Оплата подтверждается только
     подписанным webhook с проверкой сайта, заказа, суммы, переданной валюты
     (если она отсутствует — используется валюта заказа) и режима.
    Заказ и состав независимы от провайдера; выполнение не изменяет платёж.
11. **Одна система для сред.** Development и production используют общий алгоритм
    сборки, публикации, отката и генератор Nginx. Не вводить отдельную схему URL
    или отдельную бизнес-логику для локальной среды.
12. **Минимальные изменения.** Сохранять JavaScript и существующий стек. Не вводить
    зависимости, абстракции, новый роутер или миграцию технологий без необходимости.
    `dist/` — генерируемые артефакты, ручные изменения в них запрещены.
13. **Mobile-first интерфейс.** Публичный сайт и административный интерфейс
     разрабатывать начиная с мобильных размеров; варианты для большей ширины
     добавлять через `min-width` media queries или container queries. Новые и
     изменяемые компоненты должны адаптироваться к доступной ширине: сетки, карточки,
     отступы и расположение элементов не должны переносить desktop-настройки колонок
     на мобильные экраны. Не допускать горизонтального переполнения страницы; таблицы
     при необходимости прокручивать в собственном контейнере. Изображения должны
     сохранять содержимое при разных соотношениях сторон, если обрезка явно не задана
     дизайном; интерактивные элементы должны быть удобны для сенсорного управления.
     Проверять UI как минимум при 320, 375, 768, 1024 px и на десктопной ширине.
     Переиспользуемые компоненты должны обеспечивать согласованное адаптивное
     поведение. Mobile-first не требует одной колонки для всех мобильных сеток;
     существующие рабочие компоненты не переписывать только ради перехода на этот
     принцип.

Число сохраняемых релизов, имена промежуточных файлов и точные версии инструментов
описывают текущую реализацию, а не являются бессрочными архитектурными запретами.
Изменение правил требует согласованной задачи и обновления этого документа;
спорные права владельца нельзя самостоятельно превращать в новое правило.
