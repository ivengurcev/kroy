# Prodamus: настройки и оплата одной позиции

Справочник реализованного сценария. Объём продукта —
[requirements.md](requirements.md#платежи), схема интеграции —
[architecture.md](architecture.md#платежи). Это не инструкция реализации
полноценного магазина или подтверждения оплаты.

## Настройка продавца

В `/admin/payments` доступны адрес формы `payformDomain`, секретный ключ
`secretKey`, сохранение и активация/отключение. Валюта — RUB, единственный
провайдер — Prodamus. Разрешена форма `<поддомен>.payform.ru`; можно вставить
HTTPS URL с корневым/пустым путём, который нормализуется в hostname.
Произвольные домены, IP, credentials, порты, query и fragment не поддерживаются.

`PRODAMUS_SYS` — полученный у Prodamus код интеграции платформы в окружении
серверного процесса. Это не поле формы сайта. В development процесс читает
`.env`, Compose при этом задаёт свои параметры подключения к БД и Nginx;
в production окружение настраивается на сервере. После изменения окружения
нужен перезапуск приложения.

Секретный ключ сохраняется только на сервере в settings JSONB. Браузер получает
лишь признак наличия ключа, а не его значение. Пустое/отсутствующее парольное
поле сохраняет прежний ключ. Кнопка удаления ключа после подтверждения удаляет
его и отключает интеграцию в одной транзакции. Серверное хранение здесь
не означает отдельного шифрования JSONB или внешнего secret vault.

Настройки провайдеров хранятся независимо. Частичный уникальный индекс допускает
одну активную систему на сайт; операции блокируют строку сайта, активация
проверяет сохранённые настройки. Готовность checkout дополнительно требует ключ
и `PRODAMUS_SYS`: сам флаг активности ещё не гарантирует доступность оплаты.

## API

Все операции настроек приватны и ограничены сайтом текущего Host:

| Метод и URL | Тело / результат |
|---|---|
| `GET /api/site/payments` | Описание провайдеров, разрешённые читаемые поля, признак ключа |
| `PATCH /api/site/payments/:provider` | `{ "settings": { "payformDomain": "shop.payform.ru", "secretKey": "..." } }` |
| `PATCH /api/site/payments/:provider/activation` | `{ "isActive": true }` или false |
| `DELETE /api/site/payments/:provider/secret-key` | Удалить ключ и отключить интеграцию |

Публичные checkout endpoints используют `Cache-Control: no-store`:

- `GET /api/payments/status` возвращает `{ "enabled": true/false }`.
- `POST /api/payments/start` принимает только `{ "productId": "<UUID>" }`
  и при успехе возвращает `{ "url": "https://..." }`.

Карточки проверяют готовность после гидратации. До ответа кнопка «Купить» скрыта,
что сохраняет одинаковую SSR- и первоначальную клиентскую разметку. Для нулевой
цены кнопка не предлагается; есть блокировка повторного запроса и сообщение об ошибке.

## Серверный checkout

Сервер определяет сайт по Host, читает опубликованную позицию его каталога,
актуальное название, положительную цену, тип service/goods и активную интеграцию.
SKU — UUID позиции, количество — 1, валюта запроса — `rub`. Клиент не задаёт
цену, тип, количество или параметры продавца. Скрытая/чужая позиция недоступна.

`server/payments/prodamus.mjs` отправляет POST form-urlencoded с `do=link`, `sys`,
`currency`, `products[0][...]` и `signature`. Подпись — HMAC-SHA256 по JSON
рекурсивно отсортированных ключей со строковыми значениями и экранированными `/`.
Тайм-аут — 10 секунд; HTTP-перенаправления запрещены, ответ ограничен 4096 байт.
Готовая HTTPS-ссылка допускается только на домен формы или `payform.ru`;
проверяется отсутствие ключа и подписи. В браузер не возвращается подписанный
запрос. `payformInit()` не используется.

Ошибки не должны раскрывать запрос/ответ провайдера, секреты или подпись в API
и логах. Доступность API — проверка конфигурации, не пробный реальный платёж.

## Миграции и эксплуатация

Миграции `202611010001`–`202611010003` создают интеграции, добавляют products.type
(service/goods, default service) и удаляют прежнюю колонку payment_url.
Старые ссылки не переносятся. Down-миграция восстанавливает пустую колонку,
но не потерянные значения. Обычный `db:migrate` выполняется в предназначенном
окружении по [инструкции](../infra/README.md); документационный аудит его не запускает.

Для работы нужны разрешённые методы оплаты у продавца, активная интеграция,
корректный ключ и `PRODAMUS_SYS`. После обновления кода клиентская кнопка
появляется на существующем сайте после обычной публикации обновлённого JS.
Изменение ключа/активности не требует пересборки для проверки при следующем
открытии страницы. Checkout всегда проверяет цену по текущей БД, даже если
статическая карточка показывает цену прежнего релиза.

В Oysite нет покупателей, заказов, истории оплат, webhook и автоматического
подтверждения результата; покупки владелец смотрит в Prodamus. Контакты покупателя
не собираются этим checkout. Страницы успеха/отказа, уведомления, налоговые
параметры, страна и способы расчёта из прежних заметок не образуют реализованный
контракт настроек Oysite и отдельно не утверждены как требования.

Для существующего PostgreSQL-теста конкурентной активации нужны отдельная БД
с миграциями, `RUN_PAYMENT_INTEGRATION_TESTS=1`, `PAYMENT_TEST_DATABASE` и
соответствующий `DATABASE_URL`. Реальные платежи автоматическими тестами не выполняются.

Ссылка на внешний протокол для последующих задач интеграции:
[Prodamus REST API](https://help.prodamus.ru/payform/integracii/rest-api/instrukcii-dlya-samostoyatelnaya-integracii-servisov).
Поведение выше сверено с локальным кодом, а не с доступностью внешнего сервиса.
