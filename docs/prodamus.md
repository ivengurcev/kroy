# Prodamus: консультации и заказы

Объём продукта — [requirements.md](requirements.md#платежи-и-заказы),
архитектура — [architecture.md](architecture.md#платежи).

## Подключение сайта

1. В `/admin/payments` укажите URL собственной формы `<поддомен>.payform.ru`
   и секретный ключ из настроек Prodamus. Допускается HTTPS URL с корневым путём,
   нормализуемый в hostname. Другие домены, IP, credentials, порты, query и fragment
   запрещены. Сохраните настройки и активируйте подключение.
2. В кабинете Prodamus, в «Настройки → URL адреса для уведомлений», укажите
   `https://<домен-сайта>/api/payments/prodamus/webhook`. Точный URL показан в админке.
   Каждый сайт использует собственный аккаунт; деньги получает продавец.
   `PRODAMUS_SYS` не требуется и может оставаться пустым. `urlNotification` в запросе
   ссылки не передаётся: без `sys` он не применяется. Полученный позднее код платформы
   можно задать в окружении, не меняя модель заказов.
3. Рекомендуется сделать телефон и email обязательными в Prodamus. Покупатель
   заполняет контакты там; дополнительной формы оформления в Oysite нет.
4. Задайте «Email для уведомлений» при необходимости. Пустое значение использует
   актуальный email единственного активного администратора сайта. Отдельного
   владельца в модели нет; при нескольких администраторах адрес задаётся явно.
   Явно сохранённый адрес не меняется при изменении профиля пользователя.

Отключение скрывает оплату, но webhook по ожидающим заказам продолжает приниматься,
пока сохранён ключ. Удаление ключа делает проверку новых webhook невозможной.
Перед сменой аккаунта/формы завершите обработку старых платежей.

## Секреты и обновление

API возвращает только `fields.secretKey.configured`, никогда сам ключ. Пустое
парольное поле сохраняет старый ключ. Ключ шифруется AES-256-GCM с отдельным nonce;
серверный ключ выводится HKDF-SHA256 из `PAYMENT_ENCRYPTION_KEY` либо `AUTH_SECRET`
(32+ символов). Значение должно храниться только в серверном окружении. В Compose
предусмотрен отдельный development-ключ.

Сохраните резервную копию серверного ключа вместе с резервной копией БД. Его смена
без перешифрования сделает сохранённые секреты нечитаемыми. Для ранее открытых
ключей повторно сохраните настройки либо выполните в нужном окружении:

```sh
bun scripts/encryptPaymentSecrets.mjs
bun scripts/encryptPaymentSecrets.mjs --apply
```

Первый вызов — dry-run, второй шифрует существующие ключи. Секреты, подписанные
запросы и ответы провайдера не выводятся в логи.

Миграция `202611050001_create_orders.sql` добавляет orders, order_items, payments,
order_notifications и email уведомлений сайта. Применять существующей командой
`db:migrate` в предназначенном окружении. После обновления публичного JS сайт
нужно опубликовать обычным способом.

## API

Приватные операции используют существующие Vyaz/Auth.js и сайт текущего Host:

| Метод и URL | Контракт |
|---|---|
| `GET /api/site/payments` | Провайдеры, читаемые поля, признак ключа |
| `PATCH /api/site/payments/:provider` | `{ settings: { payformDomain, secretKey?, testMode? } }` |
| `PATCH /api/site/payments/:provider/activation` | `{ isActive: boolean }` |
| `DELETE /api/site/payments/:provider/secret-key` | Удалить ключ и отключить подключение |
| `GET/PATCH /api/site/order-notifications` | Ответ `{ email, defaultEmail }`; запись `{ email: string }`, пустое значение возвращает к умолчанию |
| `GET /api/site/orders` | `{ orders, hasMore }`; `status=pending|paid|completed`, `offset`, по 50 записей, новые сверху |
| `GET /api/site/orders/:id` | Заказ со снимком состава и платежами |
| `POST /api/site/orders/:id/complete` | Выполнить оплаченный заказ без изменения платежа |

Публичный API возвращает `Cache-Control: no-store`:

| Метод и URL | Контракт |
|---|---|
| `GET /api/payments/status` | `{ enabled: boolean }` без настроек |
| `POST /api/payments/start` | Только `{ productId: UUID }` → `{ url }` |
| `POST /api/payments/prodamus/webhook` | Подписанное уведомление, HTTP 200 `success` после фиксации транзакции |
| `GET /api/payments/orders/:token` | Только id, paymentStatus, fulfillmentStatus, providerStatus, isTest; без контактов |

## Создание заказа и ссылки

Сервер проверяет активное подключение, опубликованную позицию своего сайта,
положительную цену и тип service/goods. Под блокировкой позиции создаются заказ,
снимок состава и отдельный платёж. Количество — 1, валюта — RUB; несколько позиций
допускаются моделью для будущего развития. Изменение или удаление каталога не
меняет историю. Ошибка генерации ссылки оставляет заказ неоплаченным.

Запрос Prodamus — POST form-urlencoded: `do=link`, `currency=rub`,
`order_id` = UUID заказа Oysite, `products[0]` с серверными name/price/quantity/sku/type,
`payments_limit=1`, `urlSuccess` и `urlReturn`. В MVP обе страницы возврата ведут на
главную сайта с `oysite_order=<256-битный случайный токен>`. `sys` передаётся только
при явно заданном `PRODAMUS_SYS`.

Подпись — HMAC-SHA256 канонического JSON: строковые значения, рекурсивная сортировка
ключей, экранирование `/`. Тайм-аут — 10 секунд, редиректы запрещены, ответ ограничен
4096 байт. Ссылка допускается только на домен формы или `payform.ru`, без ключа
и подписи запроса. Клиент не задаёт цену, тип или параметры продавца.

После возврата компонент показывает фактический статус и ограниченно опрашивает
сервер. До webhook показывается ожидание подтверждения даже после `urlSuccess`.
Есть ручное обновление статуса.

## Webhook

Форматы — `application/x-www-form-urlencoded`/`multipart/form-data` с PHP bracket-ключами и JSON,
максимум 64 КиБ. Заголовок `Sign` проверяется ключом текущего сайта с constant-time
сравнением. Поля имеют разные назначения:

- `order_num` — UUID заказа **Oysite**, переданный при создании ссылки как `order_id`;
- `order_id` — внешний идентификатор **Prodamus**.

Проверяются существование заказа/платежа, сайт, домен формы, точная сумма до
копейки, RUB и тестовый режим. `sum` — полная сумма до комиссии. Сохраняются
customer_phone/customer_email/customer_extra и дата платежа `date` (ISO с часовым
поясом). Отсутствующие контакты остаются неизвестными.

`success` подтверждает платёж и заказ. `order_canceled` и `order_denied` отмечают
неуспешный платёж; заказ остаётся неоплаченным. Позднее неуспешное событие не
отменяет подтверждённую оплату. Неизвестные статусы, подписки и автоплатежи отклоняются.

Блокировки и транзакция, уникальность внешнего ID в пределах провайдера/формы и
единственное событие order.paid защищают от конкурентных дублей. Произвольный
webhook не создаёт заказ. Выполнение в админке не меняет сумму, дату оплаты или
подтверждённые данные платежа.

## Email-уведомления

order_notifications — транзакционная очередь. Событие создаётся вместе с оплатой
один раз. Payload содержит получателя, сайт, номер и состав заказа, сумму, дату
оплаты, контакты и ссылку `/admin/orders?order=<UUID>`, открывающую модальное окно.

`server/notifications/orders.mjs` предоставляет `setOrderNotificationTransport(send)`
и `dispatchOrderNotifications()`. Транспорт получает `{ to, subject, text, idempotencyKey }`
и обязан дедуплицировать отправку по этому ключу при повторах после сбоя процесса.
При подключении транспорта обработчик следует вызывать периодически для доставки
накопленных событий и повторов после ошибок. Сейчас транспорт не выбран: события
сохраняются, письма фактически не отправляются. Это не блокирует webhook и заказы.

## Проверка и деморежим

Автотесты используют существующий `node --test`, отдельную БД с миграциями,
`RUN_PAYMENT_INTEGRATION_TESTS=1`, `PAYMENT_TEST_DATABASE` с `test` в имени,
`DATABASE_URL` именно этой БД и тестовый `PAYMENT_ENCRYPTION_KEY`.
Автотесты не проводят реальные платежи и не запускают браузер.

Для проверки Prodamus используйте отдельные тестовые сайт/аккаунт, доступный
извне webhook и тестовый режим в Oysite: ссылка передаёт `demo_mode=1` и сквозной
`_param_oysite_test=1`. Тестовые заказы помечены в БД и админке; тестовый webhook
не подтверждает боевой заказ. Подпись с ключом `secretKey + 'demo'` допускается
только для помеченного тестового события; обычная подпись также поддерживается.
Не включайте глобальный деморежим в кабинете боевой формы: в одном из двух
режимов Prodamus не меняет подпись. Отдельный тестовый аккаунт нужен дополнительно.

Проверьте успех, отмену, отказ, повтор с растущим attempt, неверную подпись,
сумму, валюту, контакты, два разных сайта, модальное окно и выполнение заказа.
Актуальные тестовые карты берите из официальной инструкции. Доступ к общей
демо-форме требует согласования с Prodamus.
