# Kroy — URL, маршрутизация и управление сайтами

**Статус:** согласованные архитектурные решения. Часть возможностей ещё не реализована.

## 1. Общий принцип

Kroy — единая мультисайтовая платформа. Одна инсталляция обслуживает множество сайтов, но каждый сайт имеет собственные страницы, настройки и область администрирования.

Разделяем три области:

1. **Центральная панель Kroy** — управление всеми сайтами, доступными пользователю.
2. **Публичный сайт** — страницы конкретного сайта на его домене.
3. **Панель `/admin`** — управление исключительно тем сайтом, на домене которого она открыта.

У каждой области собственные URL и правила доступа.

## 2. Целевая структура URL

Домены условные.

```text
kroy.example
│
├── Основной сайт платформы
│   └── Описание продукта, регистрация и т. п.
│
app.kroy.example
│
├── /sites
│   └── Список доступных пользователю сайтов
├── /sites/new
│   └── Создание сайта
└── /sites/:siteId/...
    └── Централизованное управление сайтом

vet.kroy.example
│
├── /
├── /services
├── /contacts
└── /admin
    ├── /pages
    ├── /pages/:pageId/edit
    └── /settings

enduro.kroy.example
│
├── /
├── /routes
└── /admin
    └── Управление только сайтом Enduro

vetclinic.ru
│
└── Тот же сайт, что и vet.kroy.example,
    на собственном домене
```

Основной сайт платформы и центральная панель могут разрабатываться независимо.

## 3. Центральная панель Kroy

Планируемый адрес: `app.kroy.example`.

Назначение:

- Просмотр всех сайтов, к которым пользователь имеет доступ.
- Создание и управление сайтами.
- Управление страницами выбранного сайта.
- Общие настройки и домены.
- Управление пользователями и их доступом — в дальнейшем.

Предполагаемые маршруты:

| URL | Назначение |
|---|---|
| `/sites` | Список сайтов |
| `/sites/new` | Создание сайта |
| `/sites/:siteId/pages` | Страницы сайта |
| `/sites/:siteId/pages/new` | Создание страницы |
| `/sites/:siteId/pages/:pageId/edit` | Редактор |
| `/sites/:siteId/settings` | Настройки |
| `/sites/:siteId/domains` | Домены |

Для внутренних маршрутов используются устойчивые идентификаторы сайта и страницы.

Переименование публичного URL страницы не должно изменять адрес её редактора.

Конкретный набор административных маршрутов может уточняться по мере реализации интерфейса.

## 4. Администрирование на домене сайта

**Принципиальное требование: каждый сайт имеет собственную панель по адресу `<домен>/admin`.**

Например:

```text
vetclinic.ru/admin
enduro.example.ru/admin
```

В такой панели:

- Можно управлять только текущим сайтом.
- Нельзя просматривать список остальных сайтов пользователя.
- Нельзя переключаться на другой сайт.
- Доступны страницы, настройки и другие разрешённые функции текущего сайта.
- Набор возможностей зависит от прав пользователя.

Сайт определяется сервером по домену запроса.

**Ограничение должно обеспечиваться на сервере и в API, а не только скрытием элементов интерфейса.**

Пользователь, открывший `/admin` на одном сайте, не должен получать данные другого сайта через изменение параметров запроса.

Центральная и локальная панели могут использовать общие React-компоненты редактора. Создавать два независимых редактора не требуется.

### Обслуживание `/admin`

Публичные страницы генерируются как статический HTML. Административная панель работает через Kroy на Vyaz.

```text
Запрос на vetclinic.ru
         │
         ▼
       Caddy
         │
         ├── /admin/*
         │       │
         │       ▼
         │    Kroy / Vyaz
         │       │
         │       ▼
         │    PostgreSQL
         │    (только текущий сайт)
         │
         ├── /api/*
         │       │
         │       ▼
         │    Kroy / Vyaz
         │
         └── Остальные пути
                 │
                 ▼
           Статический сайт
```

`/admin` и `/api` — зарезервированные служебные пути, которые нельзя использовать для обычных страниц сайта.

## 5. Публичные URL

Публичные страницы имеют обычные адреса относительно корня домена:

```text
vetclinic.ru/
vetclinic.ru/services
vetclinic.ru/contacts
```

Каждый такой URL в целевой архитектуре имеет собственный предварительно сгенерированный HTML. Caddy не перенаправляет неизвестные публичные пути на общий `index.html`: существующая страница получает `200`, прежний адрес — `301`, удалённый — `410`, неизвестный — `404`.

После загрузки HTML и React-гидратации внутренние переходы выполняются через History API без полной перезагрузки. Данные всех активных страниц встроены в общий клиентский bundle, поэтому переходы и Back/Forward не требуют сетевых запросов. При прямом открытии или обновлении URL сервер по-прежнему возвращает HTML именно этой страницы.

В базе данных страница хранит только относительный путь:

```text
sites
└── vet
    ├── pages
    │   ├── /
    │   ├── /services
    │   └── /contacts
    │
    └── domains
        ├── vet.kroy.example
        └── vetclinic.ru
```

Домен не является частью данных страницы.

Один сайт может быть доступен по техническому домену платформы и собственному домену клиента.

В дальнейшем предусматриваются основной домен и перенаправления с дополнительных доменов.

Технические имена вроде `app`, `api` и `www` необходимо резервировать.

## 6. Связь с базой данных

Минимальная модель:

```text
┌─────────────────────────┐
│ sites                   │
├─────────────────────────┤
│ id                      │
│ slug                    │
│ name                    │
└─────────────────────────┘
    │
    ├── 1 : N pages
    │         id, site_id, path, title, content (JSONB)
    │
    └── 1 : N domains
              id, site_id, hostname
```

Ограничения:

- `sites.slug` уникален.
- `pages.site_id` ссылается на существующий сайт.
- `pages(site_id, path)` уникален.
- Каждая страница содержит документ с упорядоченным массивом `{part, props}`.
- `domains.site_id` ссылается на существующий сайт.
- `domains.hostname` уникален и хранится в нижнем регистре без схемы, порта и завершающей точки.

Текущий сайт определяется по нормализованному заголовку `Host`: запись в `domains` связывает hostname с сайтом. `X-Forwarded-Host` от клиентского запроса не используется.

`slug` — техническое имя сайта, не его домен. Оно может использоваться в именах каталогов сборки и локальных инструментах.

## 7. API

Все операции с данными выполняются общим приложением Kroy через инфраструктуру Vyaz.

API конкретной страницы всегда работает в контексте сайта, определённого по домену запроса:

```text
GET /api/pages
GET /api/pages?deleted=1
POST /api/pages
GET /api/pages?path=/
GET /api/pages/:pageId
PATCH /api/pages/:pageId
PUT /api/pages/:pageId
DELETE /api/pages/:pageId
POST /api/pages/:pageId/restore
```

Каждый запрос соединяет `pages` с `domains` и проверяет точное совпадение нормализованного `Host` с `domains.hostname`. Клиент не передаёт `siteId`; страница другого сайта возвращает `404` даже при известном UUID.

`GET /api/pages` без параметров возвращает только `id`, `path` и `title` страниц текущего сайта. Для существующего сайта без страниц возвращается пустой массив.

`POST /api/pages` создаёт пустую страницу текущего сайта по переданным `title` и `path`. Сайт выбирается только через домен запроса; одинаковый путь допустим на разных сайтах, но не может повторяться внутри одного сайта или занимать путь из `redirects`.

`PATCH /api/pages/:pageId` изменяет название, путь или оба поля страницы текущего сайта. Путь существующей главной страницы `/` изменять нельзя. При изменении пути прежний адрес сохраняется в `redirects` со ссылкой непосредственно на UUID страницы; повторные переименования не создают цепочек. Возврат к собственному прежнему адресу удаляет его из редиректов и резервирует покидаемый адрес.

POST и изменение пути выполняются в транзакциях с блокировкой строки сайта. Это сериализует резервирование путей между `pages` и `redirects`. Сборщик формирует из сохранённых данных правила `301` и `410`, а локальный Caddy применяет их в preview. Их согласованная production-публикация пока не реализована.

`DELETE /api/pages/:pageId` устанавливает `deleted_at` и сохраняет запись вместе с содержимым. Удалённые страницы исключаются из GET, PUT и PATCH, но продолжают занимать свой путь. Главную страницу удалить нельзя.

`GET /api/pages?deleted=1` возвращает удалённые страницы текущего сайта без содержимого. `POST /api/pages/:pageId/restore` снимает отметку удаления, сохраняя UUID, путь, название и содержимое. Окончательное удаление пока не реализовано.

При сохранении `content` страницы обновляется целиком. `site_id`, `path` и `title` через этот метод не изменяются.

Центральная панель не является исключением: её домен получает доступ только к страницам сайта, явно связанного с ним в таблице `domains`.

Публичные динамические функции (формы, отзывы и т. д.) впоследствии также используют общий API.

## 8. Локальная разработка

### 8.1. Текущий этап

Тестовый сайт `demo` связан с доменом `demo.localhost`. API страниц определяет сайт через таблицу `domains`.

```text
demo.localhost:8080           test.localhost:8080
    │                             │
    ├── / → dist/sites/demo      ├── / → dist/sites/test
    ├── /admin/* ────────────────┼── /admin/*
    └── /api/* ──────────────────┴── /api/*
                         │
                         └── общий Vyaz на хосте:3000
```

Список страниц текущего сайта доступен на `/admin/pages`, а выбранная страница открывается на `/admin/pages/:pageId/edit`. Маршрут `/admin` сохраняет совместимость и загружает главную страницу с `path = '/'`.

Новая версия статического сайта подготавливается в:

```text
dist/kroy/staging/demo/
├── index.html
├── services/index.html
├── about/team/index.html
└── routing.json
```

В целевой сборке рядом с HTML появится общий для страниц сайта клиентский React-runtime, CSS и другие ресурсы. Это не отдельное приложение на каждый URL и не SPA с единственным HTML-файлом.

Команда `yarn site:build <slug>` получает активные страницы сайта из PostgreSQL и только подготавливает HTML, ресурсы и правила в `dist/kroy/staging/<slug>/`. Действующие `dist/sites/`, файлы маршрутизации и конфигурация Nginx при этом не изменяются. `yarn site:publish <slug>` под общей PostgreSQL-блокировкой выполняет сборку и публикацию, создаёт неизменяемый релиз, переключает Nginx на его каталог и правила, затем оставляет пять последних успешных релизов сайта.

Временные маршруты вида `/_sites/:slug/...` не вводим.

### 8.2. Локальные поддомены `.localhost`

Для работы с несколькими сайтами используются локальные поддомены:

```text
app.localhost:3000
    └── Центральная панель

vet.localhost:3000
    ├── /
    ├── /services
    └── /admin

enduro.localhost:3000
    ├── /
    └── /admin
```

Преимущества:

- Один сервер и один порт.
- URL повторяют продакшен.
- Один механизм определения сайта по домену.
- Не нужна отдельная система маршрутов для разработки.
- Можно одновременно открывать несколько сайтов.

Hostname не преобразуется в `slug`: локальные поддомены и произвольные пользовательские домены обрабатываются одинаково через таблицу `domains`.

### 8.3. Принцип

**Не разрабатывать два независимых механизма маршрутизации — один для локальной среды и другой для продакшена.**

Локальная разработка использует тот же принцип определения сайта по имени хоста, что и рабочая система.

## 9. Сборка публичных сайтов

Структура артефактов:

```text
dist/
├── public/          # Клиентская сборка Vyaz
├── ssr/             # SSR-сборка Vyaz
├── kroy/            # Внутренние артефакты
│   └── staging/      # Подготовленные версии сайтов
└── sites/
    ├── vet/
    │   ├── index.html
    │   └── ...
    └── enduro/
        ├── index.html
        └── ...
```

Публичные сайты используют SSG: каждый URL получает собственный HTML. Целевая архитектура дополняет этот HTML React-гидратацией и SPA-навигацией после загрузки страницы.

Сейчас реализованы генерация готового HTML, общие JavaScript- и CSS-bundle сайта, гидратация и синхронная SPA-навигация по встроенному реестру страниц. CSS включает общие стили сайта, глобальные импорты и CSS Modules используемых запчастей. Используемые изображения и шрифты публикуются с хешированными именами в `/assets/`.

Административные страницы не входят в статическую сборку сайтов. Они обслуживаются Kroy/Vyaz.

Подготовленные и опубликованные сайты разделены по каталогам. `site:build` изменяет только `dist/kroy/staging/<slug>/`, а `site:publish` сначала обновляет staging, затем создаёт `dist/sites/<slug>/<release-id>/`. URL ресурсов содержат release-id, поэтому страницы из одного из пяти сохранённых релизов продолжают загружать соответствующие JS, CSS, изображения и шрифты после следующего переключения.

Локальная публикация согласованно переключает HTML, клиентские ресурсы и правила `301`/`410` через конфигурацию Caddy. Production-механизм публикации пока не реализован.

## 10. Авторизация и безопасность

В будущем необходимо обеспечить:

- Авторизацию в центральной панели.
- Авторизацию в панели `/admin` конкретного сайта.
- Проверку доступа к сайту на сервере.
- Изоляцию сайтов в API.
- Корректную работу с собственными доменами клиентов.
- Безопасную передачу информации об исходном домене через Caddy.

Cookie разных доменов не могут произвольно использоваться совместно. Конкретная схема авторизации для `/admin` и центральной панели пока не выбрана.

Наличие доступа к нескольким сайтам не отменяет ограничения локальной панели `/admin` одним сайтом.

## 11. Текущий статус

**Реализовано:**

- Kroy работает на Vyaz.
- Один локальный Caddy обслуживает публичные сайты, редакторы и API через `demo.localhost:8080` и `test.localhost:8080`.
- Запчасти обнаруживаются автоматически.
- Документ страницы имеет формат `{part, props}`.
- Для каждой активной публичной страницы генерируется HTML; общий React-bundle содержит реестр страниц, гидрирует разметку и управляет SPA-навигацией.
- Артефакты разделены внутри `dist/`.
- PostgreSQL хранит сайты, страницы и связанные с сайтами домены.
- API загружает страницу по пути или UUID и сохраняет её по UUID.
- API возвращает список страниц текущего сайта без их содержимого.
- API создаёт пустые страницы текущего сайта с проверкой заголовка и пути.
- API изменяет название и путь страницы, кроме пути существующей главной страницы.
- API мягко удаляет и восстанавливает страницы, сохраняя их содержимое и занятый путь.
- Доступ к страницам изолирован точным соответствием `Host` записи в таблице `domains`.
- Редактор `/admin` загружает главную страницу текущего домена и сохраняет её по кнопке.
- `/admin/pages` показывает список страниц, `/admin/pages/trash` — корзину, а `/admin/pages/:pageId/edit` открывает выбранную страницу в том же редакторе.

**Следующие этапы:**

1. Согласованная production-публикация HTML, ресурсов, данных страниц и правил маршрутизации.
2. Центральная и расширенная доменная административная панель.
3. Авторизация и права доступа.

Не реализовывать все этапы одновременно. Продолжаем работу небольшими проверяемыми задачами.

---

**Главное архитектурное правило:** центральная панель управляет множеством сайтов, `/admin` управляет только текущим сайтом, публичные страницы не зависят от административной маршрутизации, а локальная разработка не должна требовать отдельной системы URL.
