# URL, API и управление сайтами

Справочник текущих маршрутов и CLI. Архитектурные границы —
[arch-rules.md](arch-rules.md); будущая центральная панель и открытые решения —
[requirements.md](requirements.md). Production использует Nginx, как и development.

## Домен и области URL

Сайт определяется точным соответствием нормализованного `Host` в `domains`.
Hostname хранится без схемы, порта и завершающей точки, в нижнем регистре.
Один сайт может иметь несколько доменов. `slug` — техническое имя для CLI и файлов,
не результат разбора поддомена. `X-Forwarded-Host` не выбирает сайт.

Nginx Kroy проксирует `/admin`, `/auth`, `/api`, `/public`, `/static`, `/uploads`
и их подмаршруты в Vyaz с сохранением URI и Host; остальное отдаёт из активного
релиза. `/_kroy/releases/<release-id>/assets/...` обращается к ресурсам
сохранённого релиза своего сайта. Неизвестный домен получает 404.

Обычные публичные пути: `/`, `/services`, `/about/team`; непустые сегменты
состоят из строчных латинских букв, цифр и дефисов. Проценты, кодировки, пробелы
и точки не принимаются. `shared/pageFields.mjs` запрещает первые сегменты
admin/api/public/static/uploads. Это не полный список инфраструктурных конфликтов:
расхождение с `/auth` и другими пространствами отмечено в
[architecture.md](architecture.md#открытые-решения-и-известные-пробелы).

Центральная панель `/sites/...` на отдельном домене пока не реализована.
Существующая `/admin` ограничена текущим сайтом даже для superadmin.

## Приватный API

Маршруты ниже имеют префикс `/api`. Доступ проверяется Vyaz/Auth.js и
`server/auth.mjs`, данные ограничиваются сайтом по Host. Передача чужого UUID не
позволяет прочитать или изменить чужую запись.

| Метод и путь | Контракт |
|---|---|
| `GET /pages` | Список без content с массивом действующих `redirects`; `?deleted=all` — включая удалённые, `?deleted=1` — только удалённые |
| `GET /pages?path=/`, `GET /pages/:pageId` | Страница с content |
| `POST /pages` | Создать пустую страницу; title/path, type/dataSource для списка |
| `PATCH /pages/:pageId` | title/path/seo; у detail — routeParam вместо произвольного path, без seo |
| `PUT /pages/:pageId` | Полностью заменить content; формат в [PARTS.md](PARTS.md) |
| `DELETE /pages/:pageId`, `POST /pages/:pageId/restore` | Мягкое удаление / восстановление |
| `POST /pages/:pageId/detail-template` | Создать один detail-шаблон для list |
| `GET /site/settings` | Общие данные настроек |
| `PATCH /site/seo` | Полностью заменить общие SEO-настройки; чтение через `/site/settings` |
| `GET/PATCH /site/theme`, `GET/PATCH /site/contact` | Тема и контакты |
| `GET/PATCH /site/catalog` | Категории и позиции каталога |
| `GET/POST /site/catalog/categories`, `PATCH/DELETE /site/catalog/categories/:id` | Разделы каталога |
| `GET/POST /site/catalog/products`, `PATCH/DELETE /site/catalog/products/:id` | Позиции каталога; GET поддерживает categoryId, search, type, status, limit и offset, возвращает total |
| `GET /site/orders`, `GET /site/orders/:id` | Заказы текущего сайта и подробности |
| `POST /site/orders/:id/complete` | Отметить оплаченный заказ выполненным |
| `GET/PATCH /site/order-notifications` | Адрес уведомлений о заказах |
| `GET /site/reviews`, `POST /site/reviews`, `PATCH/DELETE /site/reviews/:id` | Управление отзывами; GET допускает status |
| `GET/POST /site/material-sections`, `PATCH/DELETE /site/material-sections/:id` | Разделы материалов |
| `GET/POST /site/materials`, `GET/PATCH/DELETE /site/materials/:id` | Материалы; список допускает `sectionId` |
| `GET /site/preview` | Сохранённые страницы, источники данных и тема |
| `GET/POST /site/publish` | Статус / запуск публикации |
| `POST /media` | Загрузка изображения |

Приватный API платёжных настроек — в [prodamus.md](prodamus.md).
Точный состав полей ответов определяется обработчиками в `server/api/`;
список страниц включает метаданные типа и шаблона, а не только id/path/title.

## Публичные страницы и история адресов

Обычная страница имеет постоянный UUID. Создание, изменение пути, удаление и
восстановление выполняются в транзакциях с блокировкой строки сайта. Путь проверяется
против действующих страниц и шаблонов; удалённые маршруты его не блокируют.
Создание/перенос автоматически удаляет пересекающиеся записи `redirects`.
Перенаправление ссылается на UUID, поэтому нет цепочек; возврат на прежний путь
также освобождает редирект. Главную нельзя переместить или удалить.
Удалённая страница сохраняет данные, UUID и путь, но не резервирует адрес.
Повторное создание переинициализирует существующий UUID: title/type/источник/раздел
берутся из нового запроса, content становится `[]`, SEO — `{}`, deleted_at,
detail_parent_id и route_param сбрасываются. Старые редиректы страницы и удалённые
зависимые detail-шаблоны с их редиректами удаляются. Действующая зависимость вызывает
409 без удаления данных. Один URL имеет максимум одну запись страницы в БД.
При переносе сохраняется UUID переносимой страницы, удалённый владелец целевого URL
и его удалённые зависимости очищаются.
Восстановление по существующему API запрещается, если маршрут занят действующей
страницей, шаблоном или чужим редиректом; оно не сбрасывает содержимое и настройки.

После публикации Nginx возвращает 200 для готовой страницы, 301 для прежнего
адреса, 410 для удалённой обычной страницы и её истории, 404 для неизвестного
URL. Нет перенаправления неизвестных путей на общий index.html.
Переиспользованные пути исключаются из 410 по фактическим HTML нового релиза;
301 также исключает старый 410. Это относится и к конкретным деталям материалов.
Сохранение, переименование и удаление в БД сами по себе не меняют текущий релиз.

Страница типа list задаёт источник materials/products/reviews. Для materials требуется `materialSectionId`; один активный список разрешён для раздела. Один связанный шаблон detail имеет путь `<list-path>/:<routeParam>` (по умолчанию slug).
Изменение пути списка меняет путь шаблона; шаблон в корзине всё ещё занимает
его связь со списком. Конкретные статические детали генерируются только для опубликованных материалов выбранного раздела. Slug раздела не определяет URL. Это не исполняемый параметризованный маршрут Nginx.

Изменение slug материала или пути родительского списка не создаёт редиректы
для старых конкретных деталей. После следующей публикации их прежние URL
получают 404, если не заняты другим текущим маршрутом; история самого списка
сохраняется как у обычной страницы. То же ограничение действует при снятии
материала с публикации или удалении шаблона.

Клиентский History API обслуживает известные страницы встроенного реестра;
переходы к деталям материалов и неизвестным URL используют HTTP. Прямой запрос
всегда обрабатывается Nginx с соответствующей HTTP-семантикой.

Перед использованием повторных адресов применить миграцию
`202611130003_unique_page_paths.sql` обычным механизмом dbmate. Она сохраняет
действующего владельца каждого URL, а среди только удалённых — последнюю удалённую
запись (при равных датах — первую по UUID). Лишние удалённые записи, их удалённые
зависимости и редиректы удаляются перед возвратом общей уникальности. При обнаружении
действующей зависимости удаляемой записи миграция целиком откатывается с ошибкой:
такие несогласованные данные требуют исправления, активный контент не удаляется.
Down возвращает частичный индекс, но не восстанавливает очищенные дубликаты.
Проверки миграции — `db/pagePathMigration.integration.test.mjs`, повторного
использования и гонок —
`server/api/pageUrls.integration.test.mjs`; запускать только на изолированной
мигрированной БД с `RUN_PAGE_INTEGRATION_TESTS=1` и `PAGE_TEST_DATABASE`, совпадающим
с именем БД из `DATABASE_URL`. Unit-проверки дерева, событий формы, API и правил —
`admin/editor/pageTree.test.mjs`, `admin/components/pageSettings.test.mjs`,
`server/api/pageUrls.test.mjs`, `server/api/pageRouting.test.mjs`.

## Управление сайтами и доменами

В development команды выполняются через `bun run dev:run <script> ...`, на VPS —
через `bun run remote <script> ...`. Ниже имена скриптов и аргументы:

```text
site:create vet vet.example.test "Семейный ветеринар"
site:list
site:info vet
site:domain:add vet second.example.test
site:domain:remove vet second.example.test
site:user:add vet user@example.org
```

Создание делает сайт с пустой главной страницей. Название необязательно,
по умолчанию равно slug; занятые slug/домены отклоняются. CLI доменов принимает
точный hostname без схемы, порта, wildcard и пути. Последний домен удалить нельзя.
Изменения domains в БД влияют на API сразу, но для обновления доменов публичного
Nginx требуется `site:publish <slug>`; одна `site:build` не переключает конфигурацию.
DNS и сертификат собственного домена этими командами не настраиваются.

Операции с релизами, удалённый запуск и диагностика — в
[infra/README.md](../infra/README.md).
