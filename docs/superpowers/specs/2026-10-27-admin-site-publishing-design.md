# Публикация сайта из административной панели — дизайн

## Цель

Дать пользователю Kroy возможность опубликовать сохранённую версию текущего сайта
из общей шапки административного интерфейса. Публикация использует существующие
`site:build` и `site:publish`, поэтому сохраняет версионирование релизов, проверку
Nginx и восстановление действующей конфигурации при ошибке.

## Выбранный подход

Сервер хранит одну фоновую задачу публикации в памяти процесса.
Приватный API определяет сайт только по `Host`, запускает существующие CLI-скрипты
последовательно и возвращает снимок состояния задачи. Клиент запускает задачу и
опросом получает стадии `Сборка` и `Публикация`, итог либо понятную ошибку.

Повторный запрос публикации для того же сайта, пока задача активна, не запускает
второй процесс. Запрос другого сайта получает понятный отказ до завершения этой
задачи: существующая сборка использует общие промежуточные файлы. Блокировка
действует только на вызовы из админки: существующие ручные команды SSH и их
поведение не меняются.

## API

- `POST /api/site/publish` — приватный запуск для сайта, найденного по `Host`.
  При уже активной задаче возвращает её текущее состояние без второго запуска.
- `GET /api/site/publish` — приватный снимок состояния задачи текущего сайта.

Состояние содержит безопасные для интерфейса поля: `status` (`idle`, `building`,
`publishing`, `success`, `error`), текст результата или ошибки и время завершения.
Не передаются секреты, переменные окружения или неограниченный вывод процессов.

## Сервер

Новый небольшой модуль публикации:

1. Находит `id` и `slug` текущего сайта запросом по домену из `Host`.
2. Запускает сначала существующий package script `site:build <slug>`, затем,
   только при успехе, `site:publish <slug>`.
3. Сохраняет ограниченный текстовый результат для диагностики в состоянии задачи.
4. При ошибке завершает задачу со статусом `error`; работающий релиз остаётся
   прежним благодаря существующему `publishSite.mjs`.
5. После завершения освобождает сайт для следующей публикации.

API остаётся `private: true`; существующий `hasAccess` дополнительно проверяет
права пользователя для `Host`, поэтому нельзя опубликовать другой сайт через
параметры запроса.

## Интерфейс

`AdminHeader` заменяет отключённую кнопку «Опубликовать» активной кнопкой.

- При несохранённых изменениях пользователь подтверждает, что в релиз попадёт
  только сохранённая версия.
- Во время активной задачи кнопка заблокирована и показывает текущую стадию.
- Под шапкой выводится компактное сообщение о завершении либо ошибка с `role=alert`.
- После успешной публикации отображается номер нового релиза, если его выводит
  существующий скрипт.
- В остальных административных разделах кнопка публикует тот же сайт; логика
  определения сайта всегда серверная, по `Host`.

## Границы

- Не меняются `site:build`, `site:publish`, релизы, PostgreSQL, Nginx, SSH-команды
  и ручная публикация.
- Не добавляются зависимости, очередь задач или отдельный worker.
- Не выполняются автосохранение, публикация черновиков или live-вывод процессов.
- Состояние активной задачи хранится в памяти и сбрасывается при перезапуске
  приложения; запуск при этом прекращается вместе с приложением.

## Проверка

- Успешный запуск создаёт один новый релиз и отображает результат.
- Ошибка сборки не запускает публикацию; ошибка публикации не меняет действующий
  релиз благодаря существующему механизму отката.
- Два клика и два пользователя текущего сайта не запускают параллельные процессы.
- Гость и пользователь без доступа не могут вызвать API; другой `Host` не влияет
  на текущий сайт.
- Несохранённые изменения дают предупреждение и не попадают в релиз.
