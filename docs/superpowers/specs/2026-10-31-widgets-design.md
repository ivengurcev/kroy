# Виджеты отображения запчастей: дизайн

## Цель

Добавить в Kroy виджеты как обратно совместимую надстройку над запчастями. Запчасть сохраняет настройки и подготовку данных, а необязательный виджет заменяет её публичное представление. Существующий документ `{ part, props }` и старые запчасти продолжают работать без миграции.

Первая вертикальная проверка выполняется для `@kroy/reviews`: текущий слайдер остаётся реализацией по умолчанию, а `@kroy/review-cards` показывает уже выбранные запчастью отзывы карточками.

## Ограничения

- Сохраняемый блок имеет вид `{ part, props }` без виджета либо `{ part, props, view: { name, props } }` с виджетом. Внутренний `id` редактора не сохраняется.
- Не меняются маршрутизация, схема БД, API отзывов, публикация и deploy.
- Не переделываются другие запчасти и не добавляются зависимости.
- Generated-файлы в `dist/` создаются скриптами и вручную не редактируются.
- Новая тестовая инфраструктура не создаётся; используются существующие проверки проекта и ручная проверка в браузере.

## Рассмотренные подходы

1. **Именованный JSDoc-контракт и текущий плоский набор props — выбран.** Запчасть и виджет объявляют одинаковый `@kroy-contract reviews`. `Page` применяет существующую подготовку данных запчасти, затем передаёт результат выбранному виджету вместе с его настройками. Это сохраняет старые компоненты без изменений и не дублирует фильтрацию отзывов.
2. **Отдельный объект `data` и адаптер каждой запчасти.** Граница данных была бы строже, но потребовала бы новой системы адаптеров и переделки существующей запчасти отзывов. Для обратно совместимой первой версии это лишняя архитектура.

## Регистрация и метаданные

В корне проекта появляется каталог `widgets/`. Виджет регистрируется каталогом с `package.json`, где `name` содержит идентификатор `@kroy/` в kebab-case, а `main` указывает React-компонент. Для первой версии создаётся `widgets/review-cards/` с именем `@kroy/review-cards`.

JSDoc непосредственно перед `export default` использует уже существующий `parsePartDoc`:

- `@kroy-title` — название в редакторе;
- `@kroy-category` — категория;
- `@param props.*` и `@kroy` — схема настроек `view.props`, отображаемая существующим `Field.jsx`;
- новый `@kroy-contract <name>` — именованный контракт совместимости.

Тот же `@kroy-contract reviews` добавляется к `@kroy/reviews`. Контракт — непрозрачная непустая строка без центрального списка допустимых значений; совместимость определяется только точным совпадением объявлений. Контракт отсутствует у остальных запчастей, поэтому для них редактор не предлагает виджеты. Пустое имя контракта считается ошибкой генерации.

Команда генерации запчастей также создаёт полный реестр виджетов и их JSON-метаданные для редактора. Реестр запчастей получает поле контракта, не меняя существующие `title`, `category` и `fields`. Для числовой настройки карточек `columns` существующая схема поля минимально расширяется значениями `default=3`, `min=1` и `max=4`; `defaultProps` и `Field.jsx` используют эти метаданные при создании и редактировании `view.props`.

## Редактор и состояние

При загрузке страницы редактор переносит `view` в своё состояние вместе с новым внутренним `id`. При сохранении сериализуются `{ part, props }` либо `{ part, props, view }`; пустое поле `view` не добавляется.

Редактор запчасти получает отдельный выбор «Отображение»:

- «По умолчанию» удаляет `view` и возвращает старый компонент запчасти;
- остальные варианты содержат только виджеты с тем же именованным контрактом;
- выбор виджета создаёт `view` с начальными значениями из его схемы;
- переключение виджета заменяет только `view`, не меняя `part.props`;
- ниже выбора показывается отдельная секция «Настройки виджета», построенная тем же `Field.jsx`.

Настройки предыдущего виджета при выборе другого не переносятся: новый виджет получает собственные значения по умолчанию. Это не затрагивает настройки данных запчасти.

Предпросмотр использует те же `parts`, `widgets`, блок и подготовленные данные, что публичный рендер. Поэтому смена отображения видна сразу после выхода из формы редактирования без отдельной логики предпросмотра.

## Совместимость и сохранение

Проверка совместимости выполняется по точному совпадению строкового контракта запчасти и виджета:

```text
part.contract === widget.contract
```

Редактор фильтрует список по этому правилу. `PUT /api/pages/:pageId` принимает старые блоки с двумя ключами и новые блоки с необязательным `view`. Для `view` проверяются точная форма `{ name, props }`, существование виджета и совпадение контракта с запчастью. Неизвестный или несовместимый виджет отклоняется как некорректный контент. Другие значения в `props` по-прежнему не получают новой универсальной схемной валидации.

Сборщик повторяет проверку существования и совместимости, чтобы явно диагностировать старые или вручную повреждённые документы до сборки.

## Публичный рендер и данные отзывов

`Page.jsx` сначала вызывает существующую логику `publicProps(part, props, contacts, catalog, reviews)`. Для `@kroy/reviews` именно здесь остаются режим `auto`, ручной список `reviewIds` и `limit`; виджет не фильтрует общий список отзывов.

Если `view` отсутствует, `Page` рендерит `parts[part]` с прежними props. Если `view` есть, он рендерит `widgets[view.name]` и передаёт:

```jsx
<Widget {...preparedPartProps} {...view.props} />
```

Настройки виджета имеют приоритет только при совпадении имён. В первой версии схемы разделены (`columns` принадлежит карточкам), поэтому коллизий нет.

`@kroy/review-cards` получает готовый массив `reviews`, заголовок, `showSubmitButton` и собственное число колонок. Он отображает адаптивную сетку из `1–4` колонок (по умолчанию `3`) с текстом, автором, дополнительной подписью, датой и фотографией при наличии. При `showSubmitButton=true` виджет показывает кнопку и использует существующую форму отправки отзыва. Пустой массив отзывов скрывает карточки, но не должен скрывать доступную форму отправки. Виджет не содержит выборку, сортировку или ограничение отзывов и не меняет существующий слайдер.

## Сборка сайта и SSR

Генератор статического реестра собирает уникальные `content[].view.name` отдельно от `content[].part` и импортирует только реально используемые виджеты. Generated-модуль экспортирует оба объекта: `parts` и `widgets`.

`renderSite.jsx` и `hydrateSite.jsx` импортируют одни и те же generated-реестры и передают `widgets` через `SiteApp` в `Page`. Благодаря этому SSR и гидратация выбирают один компонент и получают одинаковые props. Существующая проверка сборки сравнивает наборы CSS Modules SSR и клиента и проверяет присутствие SSR-классов в клиентских ресурсах.

## Проверка

- Выполнить `git diff --check` через обязательного проектного `git-manager`.
- Запустить одну профильную команду сборки в уже готовом Compose-окружении: генерацию реестров и сборку тестового сайта с блоками отзывов без `view` и с `@kroy/review-cards`.
- Убедиться по артефактам сборки, что неиспользуемые виджеты не импортированы и SSR/клиент прошли встроенную проверку одинаковых CSS Modules.
- В браузере вручную проверить: старый слайдер без миграции; выбор карточек; начальные три колонки и диапазон `1–4`; кнопку и форму отправки; неизменность режима/лимита/ручного списка при переключении; сохранение; повторную загрузку; возврат к отображению по умолчанию.

## Не входит

Универсальные схемы данных, миграции существующих страниц, адаптеры всех запчастей, наследование настроек между виджетами, динамические импорты, новые API/таблицы, изменение публикации и автоматический deploy.
