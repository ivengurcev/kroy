# Предпросмотр сайта Kroy

## Назначение

Предпросмотр показывает сохранённое состояние текущего сайта прямо из PostgreSQL до публикации. Он доступен только авторизованному пользователю с доступом к сайту текущего `Host` и не запускает сборку или публикацию.

## Интерфейс

- Кнопка «Предпросмотр» в `AdminHeader` открывает новую вкладку.
- Из редактора открывается текущий `page.path`, из остальных разделов — `/`.
- При несохранённых изменениях перед открытием показывается предупреждение, что предпросмотр содержит только сохранённую версию.
- Сам сайт отображается без административной шапки, рамок и контролов.
- Поверх сайта закреплена компактная плашка «Предпросмотр · сохранённая версия». Она не участвует в геометрии публичной страницы и не попадает в публикацию.

## Данные и доступ

- Добавляется приватный API-обработчик, возвращающий сохранённые неудалённые страницы текущего сайта и настройки темы.
- Сайт определяется только через существующий `getHostname(c)` и таблицу `domains`.
- Доступ защищается существующими `auth` и `hasAccess`; идентификатор сайта не принимается из query или тела запроса.
- Отсутствующий или удалённый путь возвращает состояние 404 внутри предпросмотра.

## Рендеринг и тема

- Страница `/admin/preview?path=...` использует существующие `SiteApp`, `Page`, `SiteRoot` и реестр настоящих запчастей.
- API рассчитывает через `getThemeTokens()` обе палитры — `light` и `dark` — с сохранёнными переопределениями.
- Для режимов `light` и `dark` выбирается соответствующая палитра. Для `system` клиент использует `prefers-color-scheme` и реагирует на его изменение.
- Токены передаются в `SiteRoot` как CSS-переменные только для поддерева сайта.

## Навигация

- `SiteApp` получает небольшой переиспользуемый адаптер URL, не отдельный роутер.
- Публичный путь `/services` отображается как `/admin/preview?path=/services`.
- Внутренние ссылки, прямое открытие, обновление страницы и `back`/`forward` работают в пределах предпросмотра.
- Внешние ссылки и ссылки с отдельной целью продолжают работать обычно.

## Рассмотренные варианты

1. Один приватный агрегирующий API и адаптер существующего `SiteApp` — выбранный вариант. Даёт согласованный снимок страниц и темы, не дублирует навигацию.
2. Список страниц плюс отдельный API-запрос для каждой страницы — отклонён из-за N+1 запросов и более сложной обработки навигации и 404.
3. Прямая серверная загрузка данных route-компонентом — отклонена, поскольку дублирует получение данных для SSR и клиента и обходит существующую API-инфраструктуру.

## Границы

- Формат БД и страниц не меняется.
- Публичная сборка и механизм релизов не меняются.
- Автосохранение не добавляется.
- Новые зависимости и отдельный сервер не требуются.
