# Система шаблонов страниц Oysite

**Статус:** техническая спецификация на ревью. Код не изменён, реализация не начата.
Документ не описывает текущее поведение; после согласования решения переносятся в
[requirements.md](../../requirements.md), [arch-rules.md](../../arch-rules.md),
[architecture.md](../../architecture.md) и профильные справочники.

**Задача:** переиспользуемая последовательность запчастей с обязательным элементом
«Содержимое страницы»; шапка и футер становятся обычными запчастями; брендинг Oysite
выделяется в отдельный системный элемент. Существующие типы страниц `standard`,
`list`, `detail` сохраняются.

**Кратко о рекомендуемом решении.** Отдельная таблица `page_templates` хранит
блоки шаблона и `slot_index`; страница хранит `template_mode`/`template_id` и
собственный content. Публичная сборка выносит используемые шаблоны в отдельный
`site-templates.mjs`, страницы ссылаются на них по `templateIndex`. Запчасти
шаблона рендерятся в глобальной теме, content страницы — в теме страницы.
Футер становится запчастью `@kroy/footer`, но его данные по-прежнему живут в
`sites.footer_settings`; шапка `@kroy/header` использует навигацию из этих же
настроек. Брендинг выносится в fixed-компонент. Спорные места и альтернативы
сведены в разделе 9.

## 1. Анализ существующей архитектуры и затрагиваемых компонентов

### 1.1. Что уже есть

| Подсистема | Текущее состояние | Что важно для шаблонов |
|---|---|---|
| Страница | `pages.content` — JSONB-массив блоков `{ part, props, view }`; `view` обязателен | Шаблон не должен копировать блоки в `content` страницы |
| Типы страниц | `standard`, `list`, `detail`; `detail` связан с `list` через `detail_parent_id` | Шаблон ортогонален типу страницы |
| Редактор | `admin/editor/Editor.jsx` загружает и сохраняет content, `EditorWorkspace.jsx` показывает живую страницу; `AdminShell.jsx` — оболочка | Максимальное переиспользование: `EditorWorkspace`, `PartEditor`, `PartControls`, `PartPicker`, `createPart` |
| Запчасти | `site/parts/<name>/prepare*.mjs`; синхронная подготовка данных | Шапка/футер должны быть обычными запчастями, без нового движка |
| Виджеты | `site/widgets/<name>/*.jsx`; получают `{ data, options, context }` | Футер переносится в виджет; брендинг из футера убирается |
| Runtime | `Page.jsx` вызывает `prepare` и рендерит виджет; `SiteApp.jsx` выбирает страницу, тему, футер | Появляется разрешение шаблона и три области рендера |
| Тема страницы | `pages.appearance`; `SiteApp` передаёт тему страницы в `SiteRoot`; футер сейчас рендерится отдельно в глобальной теме | Нужно сохранить глобальную тему футера и тему содержимого страницы |
| Системный футер | `SiteFooter.jsx` вне content, всегда после страницы; настройки в `sites.footer_settings`; ссылки по UUID страниц; брендинг внутри футера | Перевести в запчасть/виджет; брендинг вынести; настройки и разрешение ссылок сохранить |
| Сборка | `build/site/buildSite.mjs` читает сайт/страницы/материалы в REPEATABLE READ, генерирует `site-pages.mjs`, `site-parts.mjs`, `site-footer.mjs`, HTML и `app.js` | Нужны шаблоны в снимке, отдельный публичный реестр шаблонов |
| Предпросмотр | `/api/site/preview` готовит страницы, темы, футер, каталог, отзывы; `/admin/preview` использует `SiteApp` | Сохранённый предпросмотр должен получать разрешённые шаблоны |
| SPA | `SiteApp` переключает страницы по встроенному реестру без запросов | Шаблон должен переключаться вместе со страницей |
| Публикация | `site:build` + immutable release; fingerprint БД; откат переключает релиз | Шаблоны входят в fingerprint; откат возвращает снимок шаблона |
| API | `PUT /api/pages/:id` заменяет content; PATCH — свойства; `PATCH /api/site/footer` — настройки футера | Нужны CRUD шаблонов, выбор шаблона страницы и сохранение общего шаблона |
| Админ-маршруты | `/admin/pages`, `/admin/footer`, настройки сайта, предпросмотр | Новый раздел «Шаблоны»; `/admin/footer` убирается |

### 1.2. Ключевые ограничения

Из [arch-rules.md](../../arch-rules.md):

- блок строго `{ part, props, view: { name, props } }`;
- временные id, выделение и подготовленные данные не сохраняются в content;
- SSR и первая клиентская разметка используют одни данные, виджеты, тему и CSS Modules;
- сохранение в БД не равно публикации;
- публичная сборка содержит только используемые запчасти/виджеты и публичные данные;
- минимальные изменения, без нового универсального движка и зависимостей;
- mobile-first для админки и публичного сайта;
- тема страницы хранит только собственные переопределения, отсутствующие значения
  наследуются от сайта;
- обязательный футер и брендинг сейчас закреплены архитектурным правилом 16.

Последнее правило придётся изменить: брендинг остаётся обязательным, но перестаёт
быть частью системного футера; футер становится запчастью шаблона. Это изменение
требует явного согласования, а не молчаливой правки правила.

### 1.3. Что не копировать и не дублировать

- Не вводить новый тип страницы и не менять `page_type`.
- Не создавать отдельный React-рендерер для шапки/футера: они используют общий `Page`.
- Не хранить подготовленные данные футера/шапки в content.
- Не дублировать блоки шаблона в `pages.content`.
- Не вводить новый роутер: маршруты добавляются в существующий `server.mjs`.
- Не добавлять тестовые зависимости и браузерную автоматизацию.

## 2. Модель данных и миграции

### 2.1. Основные сущности

```text
site
  ├── page_templates (включая системный «Основной»)
  ├── pages (template_mode + template_id)
  └── footer_settings (существующие настройки, остаются на уровне сайта)
```

- **Шаблон** — сайт-специфичная запись: имя, массив блоков, позиция слота.
- **Слот «Содержимое страницы»** — не блок и не запчасть, а целочисленный индекс
  `slot_index` в массиве блоков шаблона.
- **Страница** — собственный `content` и ссылка на шаблон.
- **Футер** — обычная запчасть `@kroy/footer`, размещаемая в шаблоне; его данные
  остаются в `sites.footer_settings` и готовятся существующим
  `prepareSiteFooter`.
- **Шапка** — обычная запчасть `@kroy/header` с минимальными настройками.
- **Брендинг** — отдельный системный компонент, не часть content и не часть футера.

### 2.2. Почему `slot_index`, а не специальный блок

Сравнение вариантов:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. `content` + `slot_index` (рекомендуется)** | Массив остаётся обычным content; `validateContent` работает без изменений; слот нельзя продублировать/удалить; нет фиктивной запчасти в реестрах и PartPicker | Нужны helpers для вставки/перемещения и проверки индекса |
| B. Специальный блок `@kroy/page-content` в массиве | Визуально один массив; слот выглядит как блок | Фиктивная запчасть попадает в реестры, API, сборку и выбор запчастей; можно случайно сохранить в content страницы; требует фильтрации и специальных проверок |
| C. Две колонки `before`/`after` | Простая модель без индекса | Нельзя естественно перемещать блок через слот; две формы вместо одной; сложнее переиспользовать редактор |

Рекомендуется **A**. Слот — это позиция между блоками, а не блок. UI рисует
маркер «Содержимое страницы» в этой позиции, но в БД и API его нет.

### 2.3. Таблица `page_templates`

```sql
CREATE TABLE page_templates (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    site_id uuid NOT NULL REFERENCES sites(id) ON DELETE CASCADE,
    name text NOT NULL,
    content jsonb NOT NULL DEFAULT '[]'::jsonb,
    slot_index integer NOT NULL DEFAULT 0,
    is_system boolean NOT NULL DEFAULT false,
    version integer NOT NULL DEFAULT 1,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT page_templates_name_check
        CHECK (char_length(btrim(name)) BETWEEN 1 AND 100),
    CONSTRAINT page_templates_content_check
        CHECK (jsonb_typeof(content) = 'array'),
    CONSTRAINT page_templates_slot_check
        CHECK (slot_index >= 0 AND slot_index <= jsonb_array_length(content)),
    CONSTRAINT page_templates_version_check CHECK (version >= 1),
    CONSTRAINT page_templates_site_id_id_key UNIQUE (site_id, id)
);

CREATE UNIQUE INDEX page_templates_one_system_per_site
    ON page_templates (site_id) WHERE is_system;

CREATE UNIQUE INDEX page_templates_site_name_key
    ON page_templates (site_id, lower(btrim(name)));
```

Свойства:

- `content` — обычный массив блоков, проверяется тем же `validateContent`;
- `slot_index` — число от `0` до `jsonb_array_length(content)`;
- `is_system` — основной шаблон; уникален в пределах сайта;
- имя уникально в пределах сайта без учёта регистра и крайних пробелов;
- `version` увеличивается при каждом сохранении и используется для
  оптимистической блокировки; `updated_at` — только для отображения. Числовой
  `version` надёжнее сравнения timestamptz: `pg` может потерять микросекунды
  при преобразовании в JS `Date`.

### 2.4. Связь сайта и страниц

```sql
ALTER TABLE sites ADD COLUMN default_template_id uuid;

ALTER TABLE sites ADD CONSTRAINT sites_default_template_fk
    FOREIGN KEY (id, default_template_id)
    REFERENCES page_templates (site_id, id);

ALTER TABLE pages ADD COLUMN template_mode text NOT NULL DEFAULT 'inherit';
ALTER TABLE pages ADD COLUMN template_id uuid;

ALTER TABLE pages ADD CONSTRAINT pages_template_mode_check
    CHECK (template_mode IN ('inherit', 'template', 'none'));

ALTER TABLE pages ADD CONSTRAINT pages_template_ref_check
    CHECK ((template_mode = 'template') = (template_id IS NOT NULL));

ALTER TABLE pages ADD CONSTRAINT pages_template_fk
    FOREIGN KEY (site_id, template_id)
    REFERENCES page_templates (site_id, id) ON DELETE RESTRICT;
```

Семантика:

| `template_mode` | `template_id` | Поведение |
|---|---|---|
| `inherit` | `NULL` | Используется `sites.default_template_id`; если он `NULL`, используется системный шаблон `is_system = true` |
| `template` | UUID | Явно выбранный шаблон текущего сайта |
| `none` | `NULL` | Страница без шаблона; только её собственный content |

`default_template_id` намеренно nullable: `NULL` означает системный шаблон.
Это упрощает создание сайта (сайт вставляется раньше шаблона) и сохраняет
инвариант «основной шаблон существует всегда» на уровне приложения и миграции.
Если требуется жёсткая гарантия на уровне БД, альтернатива — `AFTER INSERT`
триггер на `sites`, создающий системный шаблон. Это единственный триггер в схеме;
решение требует отдельного согласования.

### 2.5. Основной шаблон и миграция существующих сайтов

Миграция создаёт по одному системному шаблону на каждый сайт:

```sql
INSERT INTO page_templates (site_id, name, content, slot_index, is_system)
SELECT s.id,
       'Основной',
       '[{"part":"@kroy/footer","props":{},"view":{"name":"@kroy/footer","props":{}}}]'::jsonb,
       0,
       true
FROM sites s
WHERE NOT EXISTS (
    SELECT 1 FROM page_templates t
    WHERE t.site_id = s.id AND t.is_system
);

UPDATE sites s
SET default_template_id = t.id
FROM page_templates t
WHERE t.site_id = s.id AND t.is_system AND s.default_template_id IS NULL;
```

Почему именно так:

- слот стоит **до** футера (`slot_index = 0`), поэтому существующие страницы
  сохраняют прежний порядок: содержимое страницы, затем футер;
- шапка **не добавляется** в основной шаблон автоматически: иначе существующие
  сайты визуально изменятся после миграции. Шапку можно добавить вручную;
- `sites.footer_settings` **не переносятся и не удаляются**: данные футера
  остаются на месте и продолжают использоваться;
- изменения футера из редактора шаблона/страницы сохраняются через существующие
  настройки сайта, а не копируются в `page_templates.content`.

Миграция должна выполняться до запуска новой версии API и сборщика. Старые
версии кода новые колонки игнорируют и продолжают работать с `footer_settings`.

### 2.6. Создание сайта и seed

Обновить:

- `scripts/createSite.mjs` — после вставки сайта создать системный шаблон
  «Основной» с блоком `@kroy/footer` и установить `default_template_id`;
- `db/seed.mjs` — то же для demo/test сайтов;
- тестовые помощники, которые вставляют `sites` напрямую: либо создавать
  системный шаблон, либо не рассчитывать на сборку/предпросмотр без него.

Если системный шаблон отсутствует, сборка и предпросмотр должны завершаться
понятной ошибкой «Основной шаблон сайта не найден», а не молча рендерить страницу
без шапки/футера.

### 2.7. Хранение футера: важное решение

Есть два практических варианта:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. `sites.footer_settings` остаётся источником истины (рекомендуется)** | Не теряются существующие данные и API; ссылки по UUID страниц разрешаются на сервере; в публичную сборку не попадают сырые UUID и настройки; одинаковые юридические данные не дублируются по шаблонам | Настройки футера не являются `props` блока; редактирование открывает отдельную панель/диалог; если в двух шаблонах разные футеры, их содержимое всё равно общее |
| B. Перенести `footer_settings` в `props` блока `@kroy/footer` | Футер становится «обычной» запчастью с props; один способ сохранения | Придётся публиковать сырые UUID/настройки или готовить данные отдельно; дублирование юридических данных по шаблонам; миграция и совместимость API; риск расхождения двух источников |

Рекомендуется **A**. Блок `@kroy/footer` — это размещение и виджет, а данные
футера — сайтовые, как и раньше. Это сохраняет [FOOTER.md](../../FOOTER.md):
внутренние ссылки разрешаются по UUID, удалённые/чужие страницы исключаются,
административные идентификаторы не публикуются.

Проверка миграции футера при варианте A: `sites.footer_settings` до и после
миграции совпадают; диалог показывает те же значения; публичный футер после
перепубликации визуально совпадает с прежним (кроме вынесенного брендинга).
Отдельного переноса данных и отдельной таблицы настроек футера нет.

### 2.8. Публичный реестр шаблонов

Нельзя встраивать полный шаблон в каждую страницу `site-pages.mjs`: один и тот же
шаблон повторится на всех страницах и раздуется клиентский bundle. Рекомендуется
отдельный модуль:

```js
// dist/kroy/site-templates.mjs
export const templates = [
    {
        before: [ /* блоки до слота */ ],
        after: [ /* блоки после слота */ ],
    },
];
```

- страница в `site-pages.mjs` и в payload детальной страницы получает
  `templateIndex` (число) или не получает его, если шаблона нет; `0` — валидный
  индекс, проверять нужно на `null`/`undefined`, а не на truthiness;
- шаблоны без блоков до/после слота в публичный реестр не попадают;
- в публичном реестре нет `id`, `name`, `slot_index`, `updated_at` и
  административных настроек — только блоки;
- SSR (`renderSite.jsx`) и гидратация (`hydrateSite.jsx`) импортируют один и тот же
  `site-templates.mjs`;
- `generateSiteParts` собирает запчасти/виджеты из `page.content`, `template.before`
  и `template.after`.

Альтернатива — хранить `before`/`after` внутри каждой страницы. Проще, но
дублирует шаблон в HTML/JS на каждой странице. Для статического сайта это
нежелательно.

### 2.9. Fingerprint и публикация

`db/siteFingerprint.mjs`:

- добавить `page_templates` в список таблиц;
- добавить `default_template_id` в JSON сайта;
- `pages.template_mode`/`template_id` попадут автоматически, так как fingerprint
  собирает `to_jsonb(pages)`.

Следствие: изменение шаблона, выбор шаблона страницей или смена шаблона по
умолчанию сразу делают сохранённое состояние неопубликованным (`hasChanges`).

## 3. Поведение редакторов и пользовательские сценарии

### 3.1. Раздел «Шаблоны»

Маршруты:

- `/admin/templates` — список шаблонов и выбор шаблона по умолчанию;
- `/admin/templates/:templateId` — редактор шаблона.

В основном меню админки добавить пункт «Шаблоны». Рекомендуемое место — группа
«Настройки» рядом с «Оформлением» и «Контактами»: шаблон по умолчанию — это
настройка сайта, а сами шаблоны влияют на все страницы. Допустимо разместить
пункт в группе «Основное» рядом со «Страницами»; в этом случае селектор шаблона
по умолчанию всё равно остаётся на странице «Шаблоны». Иконка — новая `templates`
или существующая `pages`; рекомендуется отдельная иконка, чтобы не путать со
страницами.

Список:

- название, бейдж «Основной», бейдж «По умолчанию», количество страниц,
  дата изменения;
- действия: открыть/изменить в редакторе, удалить (кроме основного);
  переименование выполняется в редакторе и сохраняется вместе с content;
- «Создать шаблон» — модальное окно с названием; после создания переход в редактор;
- селектор «Шаблон по умолчанию»; при наличии страниц с `inherit` — подтверждение,
  потому что изменение затронет все такие страницы. Количество для подтверждения
  берётся из `usage.inheritedPages` текущего шаблона по умолчанию;
- удаление используемого шаблона блокируется с понятным сообщением и списком
  страниц; автоматического переноса страниц нет.

Пустой шаблон создаётся с `content = []`, `slot_index = 0` — страница без
шапки/футера, пока пользователь не добавит запчасти.

### 3.2. Редактор шаблона

Максимально переиспользует существующий редактор:

- `EditorWorkspace`/`PartEditor`/`PartControls`/`PartPicker`;
- `createPart`, `changePartView`, `Field`, `ListField`, `ImageField`;
- существующие `ActionFooter`, `AdminPageShell`, `apiRequest`, navigation guard.

Отличия:

- вместо `pages.content` редактируется `page_templates.content`;
- в позиции `slot_index` показывается нередактируемый маркер
  «Содержимое страницы»;
- до и после маркера можно добавлять, удалять, перемещать и редактировать любые
  запчасти;
- маркер нельзя удалить, продублировать, переместить или открыть как запчасть;
- сохранение — `PUT /api/templates/:id` с `expectedVersion`;
- кнопки «Сохранить» и «Отмена»; «Отмена» возвращает загруженное состояние;
- удаление — только для дополнительного шаблона, с подтверждением;
- живой предпросмотр показывает запчасти шаблона; вместо содержимого страницы —
  нейтральный маркер/заглушка. Полноценная страница показывается в редакторе
  страницы;
- запчасти, зависящие от `record`/списка материалов, в редакторе шаблона могут
  выглядеть пусто или приблизительно: у шаблона нет конкретной записи. Это
  допустимо; проверка таких блоков выполняется на странице.

Перемещение блока через слот:

- блок можно переместить из «до» в «после» и наоборот;
- сам маркер остаётся на месте;
- все операции идут через helpers, которые синхронно правят `slot_index`.

Правила `slot_index` (S — текущая позиция, N — длина массива):

| Операция | Изменение массива | Изменение S |
|---|---|---|
| Вставка перед слотом | `content.splice(S, 0, block)` | `S + 1` |
| Вставка после слота | `content.splice(S, 0, block)` | без изменений |
| Удаление блока с индексом `i < S` | удалить `content[i]` | `S - 1` |
| Удаление блока с индексом `i >= S` | удалить `content[i]` | без изменений |
| Перемещение блока из `i < S` в `j >= S` | переставить | `S - 1` |
| Перемещение блока из `i >= S` в `j < S` | переставить | `S + 1` |
| Перемещение внутри одной стороны | переставить | без изменений |

Границы: `0 <= S <= N`. API повторно проверяет `slotIndex` и отклоняет
некорректное значение, даже если интерфейс уже проверил его.

### 3.3. Настройка «Использовать шаблон» в редакторе страницы

Разместить компактную панель над рабочей областью страницы (не в отдельном
модальном окне), чтобы выбор сразу отражался в живом предпросмотре. На узком
экране селектор занимает доступную ширину и не создаёт горизонтального
переполнения; подпись и значение не обрезаются без доступного полного текста.

Варианты:

1. «Наследовать шаблон сайта — „Основной“» (`inherit`);
2. конкретный шаблон из списка (`template`), включая «Основной»;
3. «Без шаблона» (`none`).

Селектор показывает эффективный шаблон при `inherit`; при смене шаблона
загружается его content. Если в текущем шаблоне есть несохранённые изменения,
смена выбора требует подтверждения: иначе правки общего шаблона будут потеряны.
Если загрузка нового шаблона не удалась, выбор откатывается к прежнему.

Сохранение выбора входит в общий `PUT /api/pages/:id` (см. 5.1), а не в PATCH
свойств страницы. Это позволяет сохранить content, шаблон и выбор шаблона одной
транзакцией.

### 3.4. Отображение полной страницы в редакторе

Редактор страницы показывает три области:

```text
[ запчасти шаблона до слота ]   ← общие, глобальная тема
[ собственные запчасти страницы ] ← content страницы, тема страницы
[ запчасти шаблона после слота ]  ← общие, глобальная тема
```

- у запчастей шаблона нет кнопок добавления, удаления и перемещения;
- у них остаётся кнопка редактирования свойств;
- точки вставки есть только внутри собственного content страницы: перед первым
  блоком, между блоками и после последнего;
- если content страницы пуст, показывается одна точка вставки и подсказка
  «Добавить запчасть»;
- если шаблон не выбран, отображается только content страницы, как сейчас;
- блоки шаблона визуально отделены (фон/рамка/подпись), чтобы не путать с
  содержимым страницы;
- `record` и `context` detail/list-страницы передаются и шаблонным, и страничным
  блокам, как при публичном рендере;
- fixed-брендинг в живом редакторе не выводится, чтобы не перекрывать
  административные контролы; он виден в сохранённом предпросмотре и публичной
  версии. Это единственное осознанное отличие живого редактора от полной страницы.

Редактирование свойств блока шаблона:

- изменения попадают в черновик шаблона, а не в `pages.content`;
- сохранение обновляет `page_templates.content`, а не страницу;
- при сохранении страницы content страницы и content шаблона сохраняются одной
  транзакцией (рекомендация);
- если шаблон изменён в другой вкладке, сервер возвращает 409 по
  `expectedVersion`; редактор не перезаписывает чужие изменения и предлагает
  перезагрузить шаблон;
- если в шаблоне осталась неизвестная запчасть (например, после удаления модуля),
  редактор страницы показывает заглушку, но не может сохранить изменения такого
  шаблона: API отклонит неизвестную запчасть. Нужно открыть редактор шаблона и
  заменить/удалить блок.

### 3.5. Предупреждающая иконка общего элемента

Рядом с управлением каждого блока шаблона в редакторе страницы постоянно видна
яркая предупреждающая иконка. Поведение:

- иконка не скрывается и не появляется только при наведении;
- цвет — существующие warning-токены админки (`--color-warning-text`,
  `--color-warning-soft`), контрастный фон;
- иконка фокусируема с клавиатуры;
- при наведении и фокусе показывается тултип:
  «Общий элемент шаблона. Изменения затронут все страницы, использующие шаблон
  „Название“»;
- для скринридеров текст связан через `aria-describedby` и `role="tooltip"`;
- на сенсорном экране фокус/тап по иконке также показывает тултип;
- тултип не создаёт горизонтального переполнения; на узком экране ширина
  ограничена `calc(100vw - 32px)`;
- иконка — кнопка `type="button"`, не отправляет форму; клик не открывает
  редактор запчасти.

Для блоков собственного content страницы иконки нет. В редакторе шаблона иконки
нет: там это не «общий» элемент, а сам шаблон.

### 3.6. Черновики, отмена и сохранение

Состояние редактора страницы:

- `pageContent` — собственный content страницы (с временными id);
- `templateDraft` — `{ id, name, content, slotIndex, version, updatedAt, isSystem }`;
- `templateMode`, `templateId` — выбор шаблона;
- `footerDraft` — черновик настроек футера для диалога (см. 3.7);
- `isDirty` учитывает все перечисленные черновики.

Правила:

- изменение свойств блока шаблона помечает dirty;
- в `ActionFooter` редактора страницы добавляется вторичная кнопка «Отмена»,
  активная при dirty; она возвращает content страницы, выбор шаблона и черновик
  шаблона к загруженным значениям. Если были несохранённые изменения общего
  шаблона, показывается подтверждение, потому что они затрагивают другие
  страницы; для футера действуют собственные «Сохранить»/«Отмена» диалога;
- смена шаблона при dirty-шаблоне требует подтверждения и сбрасывает черновик
  старого шаблона;
- `Save` отправляет content страницы, выбор шаблона и (если изменён) content
  шаблона одним запросом; при ошибке ни страница, ни шаблон не сохраняются;
- свойства страницы (title/path/SEO/appearance) по-прежнему сохраняются отдельным
  `PATCH`. Если черновик шаблона dirty, PATCH его не сохраняет: после закрытия
  диалога настроек в редакторе остаётся общий `Save`, а индикатор несохранённых
  изменений не сбрасывается;
- публикация блокируется, пока есть несохранённые изменения (существующий
  `publicationBlocked`);
- если шаблон изменён в другой вкладке и страница тоже сохраняет шаблон — 409,
  черновики сохраняются, показывается сообщение и действие «Перезагрузить шаблон»;
- если шаблон изменился, но страница сохраняла только свой content, ответ с новой
  `template.version` позволяет редактору перезагрузить шаблон, не теряя content
  страницы и не выдавая старый предпросмотр за актуальный;
- если шаблон по умолчанию изменён, пока страница наследует его, сохранение
  возвращает 409 `default_template_changed`; редактор перезагружает шаблон;
- если выбранный шаблон удалён, сохранение возвращает 409/404; редактор
  перезагружает список и просит выбрать шаблон. Удаление используемого шаблона
  сервером блокируется, поэтому это возможно только при внешнем изменении данных.

Отдельного многоуровневого undo нет: «отмена» — это существующая семантика
возврата к сохранённому состоянию.

### 3.7. Футер: настройка из редактора

Настройки футера остаются в `sites.footer_settings`, но отдельная страница
`/admin/footer` удаляется.

- В шаблоне есть блок `@kroy/footer`.
- В PartPicker обычной страницы системные `@kroy/header` и `@kroy/footer`
  рекомендуется скрыть, чтобы не создавать второй футер/шапку; в PartPicker
  шаблона они доступны (см. 9.1, вопрос 7). Для этого PartPicker получает
  признак режима «страница/шаблон» и список исключений; API при этом не
  запрещает такие блоки в content, если продукт решит иначе.
- У блока нет собственных data-полей; его виджет не имеет обязательных настроек.
- Кнопка редактирования блока открывает диалог «Настройки футера» с существующей
  формой `FooterSettings` (описание, навигация, документы, реквизиты). Подпись
  «Навигация» рекомендуется уточнить как «Навигация сайта», потому что её
  использует и шапка; значения и формат не меняются.
- Диалог сохраняет через существующий `PATCH /api/site/footer`; после сохранения
  редактор обновляет подготовленный футер для живого предпросмотра.
- Диалог имеет собственные «Сохранить»/«Отмена»; его dirty state участвует в
  navigation guard и блокировке публикации (как `PageDetailsDialog` сейчас).
  При несохранённых изменениях Отмена/закрытие диалога требуют подтверждения.
- Изменения футера общие для всех страниц и шаблонов; это подчёркивается текстом
  в диалоге.
- Сохранение шаблона (`PUT /api/templates/:id`) и сохранение страницы не
  сохраняют настройки футера: это делает только диалог через
  `PATCH /api/site/footer`. Индикатор несохранённых изменений учитывает оба
  черновика.
- В редакторе шаблона доступна отдельная команда «Настройки футера и навигации»,
  открывающая тот же диалог даже при отсутствии блока `@kroy/footer`. Это нужно,
  чтобы навигацией шапки можно было управлять без добавления футера; отдельной
  страницы настроек не появляется.
- Если футер удалён из шаблона, на публичной странице его нет; брендинг Oysite
  остаётся.

Почему диалог, а не сохранение в общем `PUT` страницы: это сохраняет текущий
контракт настроек сайта и не смешивает сайтовые юридические данные с content
шаблона. Альтернатива — включить `footer` в `PUT` страницы и сохранять всё одной
транзакцией; это больше меняет API и публичную модель данных.

### 3.8. Шапка

Запчасть `@kroy/header` с минимальными настройками:

- `title` — необязательный текст; пусто означает `siteName`;
- `logo` — необязательное изображение;
- `showName` — показывать название (по умолчанию да);
- `showNavigation` — показывать навигацию (по умолчанию да);
- `showPhone` — показывать телефон из контактов (по умолчанию да).

Навигация шапки в MVP использует **существующую навигацию сайта из настроек
футера** (`footer.navigation`), уже разрешённую по UUID в `prepareSiteFooter`.
Это избегает нового типа поля «ссылка на страницу», дублирования навигации и
попадания UUID в публичный content. Если нужна отдельная навигация шапки, это
следующее расширение (см. 9).

Шапка — обычная запчасть: её можно добавить в шаблон до слота. Отдельного
механизма рендеринга нет. Виджет выводит `header`, ссылку на `/`, навигацию и
телефон; mobile-first, без горизонтального переполнения. Если все элементы
скрыты или пусты, пустой `header` не выводится.

### 3.9. Пользовательские сценарии

1. Администратор открывает «Шаблоны», видит «Основной», создаёт «Лендинг».
2. В «Лендинге» добавляет шапку до слота, футер после слота, сохраняет.
3. В настройках сайта/на странице шаблонов выбирает «Лендинг» по умолчанию.
4. Открывает страницу с `inherit`: видит шапку, свои блоки, футер; шапка и футер
   помечены как общие.
5. Меняет заголовок шапки: изменение сохраняется в шаблоне; другие страницы с
   этим шаблоном видят его после сохранения.
6. На другой странице выбирает «Без шаблона»: остаются только её блоки; брендинг
   Oysite остаётся.
7. Пробует удалить «Лендинг», используемый страницами: получает отказ со списком
   страниц; сначала переназначает их.
8. Пробует удалить «Основной»: действие недоступно.
9. Открывает футер из редактора шаблона, меняет навигацию, сохраняет; публичный
   вид обновляется после публикации сайта.
10. Открывает две вкладки с одной страницей, меняет общий шаблон в обеих:
    вторая получает конфликт версии и не перезаписывает первую.

## 4. Схема рендеринга и публикации

### 4.1. Публичное дерево

```jsx
<>
  <SiteTheme global>                         // глобальная тема сайта
    {template.before.length > 0 && (
      <Page content={template.before} ... />
    )}

    <SiteTheme page>                         // тема конкретной страницы
      <PaymentResult />                      // один раз, как сейчас
      <Page content={page.content} ... />
    </SiteTheme>

    {template.after.length > 0 && (
      <Page content={template.after} ... />
    )}
  </SiteTheme>

  <OysiteBranding />                         // fixed, вне темы и content
</>
```

Если шаблона нет или в нём нет блоков до/после слота, рендерится только
страница в её теме (как сейчас). `PaymentResult` остаётся в поддереве темы
страницы, чтобы не менять текущее поведение. `SiteRoot` можно сохранить для
редактора и точечного рендера; публичный `SiteApp` использует `SiteTheme`
напрямую, чтобы не вкладывать `SiteRoot` и не дублировать `PaymentResult`.

### 4.2. Тема шаблонных запчастей

Рекомендуется: **запчасти шаблона до/после слота используют глобальную тему
сайта; content страницы — тему страницы (`pages.appearance`)**.

Причины:

- текущий футер по [FOOTER.md](../../FOOTER.md) всегда использует глобальную тему;
- шапка и футер — общие элементы сайта, а не содержимое конкретной страницы;
- страница с индивидуальной тёмной/другой темой не должна менять оформление
  юридического футера и шапки.

Следствие: произвольная запчасть, добавленная в шаблон (например, CTA или
разделитель), тоже использует глобальную тему. Это осознанное правило: шаблон —
это «оболочка сайта», content — страница.

Альтернатива: все запчасти, включая шаблонные, используют тему страницы. Проще
(один wrapper), но меняет текущее поведение футера на страницах с appearance.
Решение требует подтверждения продукта/дизайна.

Визуальный риск: вложенные `SiteTheme` создают дополнительные DOM-обёртки;
правило `.section:first-child` может убрать верхний отступ у первой секции
каждой области. Это нужно проверить вручную на страницах с шапкой, без шапки,
с футером и без него.

### 4.3. Подготовка данных для шапки и футера

`Page` получает подготовленный `footer` (из `site-footer.mjs` или API
предпросмотра) и передаёт его в `prepare`:

```js
prepare({
  props,
  record,
  context,
  contacts,
  catalog,
  reviews,
  materials,
  materialSectionId,
  footer, // подготовленная модель футера, без сырых UUID
})
```

- `prepareFooter({ footer, contacts })` возвращает данные для виджета;
- `prepareHeader({ props, contacts, footer })` использует `footer.siteName` и
  `footer.navigation`;
- остальные запчасти дополнительный аргумент игнорируют;
- в публичную сборку по-прежнему попадает только подготовленный `site-footer.mjs`,
  без `footer_settings` и UUID.

### 4.4. SSR и гидратация

- `buildSite.mjs` разрешает шаблон для каждой страницы в том же REPEATABLE READ,
  что сайт и страницы;
- в `site-templates.mjs` попадают только используемые шаблоны, без id/имени;
- `renderSite.jsx` и `hydrateSite.jsx` импортируют один `site-templates.mjs` и
  передают `templates` в `SiteApp`;
- `SiteApp` по `page.templateIndex` выбирает шаблон и рендерит три области;
- серверная и первая клиентская разметка совпадают: нет fetch, `Date.now()`,
  `window` или случайных данных в шаблоне;
- `site-footer.mjs` готовится один раз и передаётся в `Page` на сервере и клиенте;
- брендинг рендерится безусловно и не зависит от темы/шаблона.

### 4.5. SPA-переходы

- `site-pages.mjs` содержит `templateIndex` для каждой обычной страницы;
- `SiteApp` при переходе берёт новую страницу и новый шаблон из встроенных
  реестров, без запросов;
- Back/Forward используют те же данные;
- если страница не найдена в реестре, поведение прежнее — обычный HTTP-переход;
- детальные страницы материалов по-прежнему открываются HTTP-переходом; их
  payload содержит `templateIndex`, а `SiteApp` получает общий `templates`.

### 4.6. Статическая сборка

Последовательность:

1. Прочитать сайт (включая `default_template_id`), страницы, detail-шаблоны и
   `page_templates` в одном REPEATABLE READ.
2. Разрешить шаблон для каждой страницы по `template_mode`/`template_id`.
3. Собрать уникальные публичные шаблоны в `site-templates.mjs` (`before`/`after`).
4. Проставить `templateIndex` страницам и detail-шаблонам.
5. Для детальных страниц материалов скопировать `templateIndex` из detail-шаблона
   (материалы наследуют шаблон своего detail-шаблона).
6. `generateSiteParts` собирает запчасти/виджеты из `page.content`,
   `template.before`, `template.after`.
7. `site-pages.mjs`, payload деталей и `site-templates.mjs` пишутся до SSR.
8. SSR и клиент используют общие реестры.

Если шаблон содержит неизвестную запчасть, действует существующее правило:
сборка предупреждает и не импортирует её, `Page` показывает заглушку. Ошибки
структуры/несовместимого виджета остаются ошибками сборки.

### 4.7. Предпросмотр

- `/api/site/preview` разрешает шаблоны для страниц и возвращает:
  - `templates: [{ before, after }]`;
  - `pages[path].templateIndex`;
  - подготовленный `footer`, как сейчас.
- `/admin/preview` передаёт `templates` в `SiteApp`.
- Живой редактор не использует публичный реестр: он загружает страницу и шаблон
  через API и строит черновик; предпросмотр обновляется сразу.
- Предпросмотр детальных шаблонов по-прежнему не поддерживается на отдельном
  экране; редактор detail-страницы при этом работает и показывает шаблон.

### 4.8. Публикация и откат

- шаблоны входят в fingerprint;
- `site:build` собирает staging с разрешёнными шаблонами; публикация
  переключает релиз целиком;
- изменение общего шаблона затрагивает все страницы, использующие его, только
  после следующей публикации;
- откат возвращает HTML/ресурсы/шаблоны из прежнего релиза, но не откатывает
  `page_templates` в БД (как и страницы сейчас);
- старые релизы не зависят от текущего состояния шаблонов;
- после миграции существующие опубликованные сайты нужно перепубликовать, чтобы
  получить новую разметку; до этого они продолжают работать на прежнем релизе.

### 4.9. Брендинг Oysite

Новый компонент `site/runtime/OysiteBranding.jsx`:

- `<a href="https://oysite.ru/">Создано на Oysite</a>`;
- всегда рендерится один раз в `SiteApp`, вне content, шаблона и футера;
- `position: fixed` в правом нижнем углу;
- учитывает `env(safe-area-inset-right/bottom)`;
- не отключается настройками, API и конфигурацией;
- не перекрывает критически важные интерактивные элементы: компактный размер,
  safe-area, нижний резерв публичной оболочки
  (`padding-block-end: calc(48px + env(safe-area-inset-bottom))`) и
  `scroll-padding-block-end`, чтобы последняя строка футера могла прокрутиться
  выше брендинга; проверка на 320/375 px;
- имеет собственные нейтральные стили, не зависит от темы сайта;
- в футере больше нет ссылки брендинга; в `SiteFooter`/`Footer` её быть не должно.

## 5. API и необходимые изменения

### 5.1. `PUT /api/pages/:pageId` — расширение

Тело:

```json
{
  "content": [ /* собственный content страницы */ ],
  "templateMode": "inherit",
  "templateId": null,
  "expectedDefaultTemplateId": "uuid",
  "template": {
    "id": "uuid",
    "content": [ /* content шаблона */ ],
    "slotIndex": 0,
    "expectedVersion": 3
  }
}
```

Правила:

- `content` обязателен и проверяется существующим `validateContent`;
- `templateMode` опционален; если передан, `templateId` должен соответствовать
  режиму (`template` — UUID, `inherit`/`none` — `null`);
- `template` опционален; если передан, его `id` должен совпадать с эффективным
  шаблоном после применения выбора;
- `expectedDefaultTemplateId` используется при `inherit`: если текущий шаблон по
  умолчанию изменился, вернуть 409 `default_template_changed`;
- `expectedVersion` проверяется под `FOR UPDATE`; несовпадение — 409
  `template_conflict` с текущей `version`;
- сайт и страница блокируются; обновление content страницы, выбора шаблона и
  content шаблона выполняется одной транзакцией;
- при любой ошибке не сохраняется ничего;
- ответ содержит поля страницы (как сейчас) плюс `templateMode`, `templateId`,
  `template: { id, name, content, slotIndex, version, updatedAt } | null`.

Обратная совместимость: запрос `{ content }` без новых полей работает как
раньше и не меняет выбранный шаблон.

### 5.2. Шаблоны

| Метод и путь | Контракт |
|---|---|
| `GET /api/templates` | `{ defaultTemplateId, templates: [{ id, name, isSystem, version, updatedAt, usage }] }`; без content |
| `POST /api/templates` | `{ name }`; создаёт пустой шаблон (`content: []`, `slotIndex: 0`); 201 |
| `GET /api/templates/:templateId` | Полный шаблон: `{ id, name, isSystem, content, slotIndex, version, updatedAt, usage }` |
| `PUT /api/templates/:templateId` | `{ name, content, slotIndex, expectedVersion }`; проверка content через `validateContent`, имени и слота; 409 при конфликте версии/имени |
| `DELETE /api/templates/:templateId` | 204; 409 `system_template`, `default_template` или `template_in_use` со списком страниц |
| `PATCH /api/site/default-template` | `{ templateId }`; обновляет `sites.default_template_id`; возвращает `{ defaultTemplateId, inheritedPages }` |

`PUT /api/templates/:id` обновляет `version = version + 1` и `updated_at = now()`
в той же транзакции. Если `expectedVersion` не совпал, возвращается 409 без
записи; клиент должен перезагрузить шаблон.

`usage`:

```json
{
  "explicitPages": 2,
  "inheritedPages": 5,
  "deletedPages": 1,
  "isDefault": true
}
```

- `explicitPages` — все страницы (включая удалённые) с
  `template_mode = 'template'` и этим `template_id`;
- `inheritedPages` — все страницы (включая удалённые) с `inherit`, если шаблон
  выбран по умолчанию;
- `deletedPages` — сколько из перечисленных страниц в корзине;
- `isDefault` — выбран ли шаблон по умолчанию.

Удаление блокируется, если `explicitPages > 0` или шаблон выбран по умолчанию;
удалённые страницы учитываются, чтобы восстановление не ссылалось на удалённый
шаблон.

Все маршруты приватны, ограничены текущим сайтом по Host. Чужой UUID шаблона
возвращает 404; передача `siteId` клиентом не допускается.

### 5.3. Страницы

- `GET /api/pages/:pageId` добавляет `templateMode`, `templateId`.
- `POST /api/pages` создаёт страницу с `inherit`; выбор шаблона доступен в
  редакторе после создания.
- `PATCH /api/pages/:pageId` не принимает поля шаблона; они сохраняются через
  `PUT` (см. 5.1). Это сохраняет текущий контракт PATCH для title/path/SEO/appearance.
- `POST /api/pages/:pageId/detail-template` создаёт detail-страницу с `inherit`.
- `reusePagePath`/создание по удалённому адресу сбрасывают `template_mode` в
  `inherit`, `template_id` в `NULL` вместе с content/SEO/appearance.
- `restorePage` сохраняет выбранный шаблон; удаление используемого шаблона
  блокируется, поэтому восстановление не должно ссылаться на удалённый шаблон.

### 5.4. Предпросмотр и футер

- `GET /api/site/preview` дополнительно возвращает `templates` и
  `pages[path].templateIndex`.
- `GET /api/site/footer` (новый, приватный): `{ settings, footer }` —
  нормализованные настройки для формы и подготовленная модель для живого
  предпросмотра.
- `PATCH /api/site/footer` остаётся без изменения контракта; после сохранения
  редактор повторно запрашивает `GET /api/site/footer`.
- `GET /api/site/settings` можно не менять; `footer` там остаётся для совместимости.
- `getSiteFooter`/`prepareSiteFooter` используются и API, и сборкой, и
  предпросмотром.

### 5.5. Валидация и ошибки

- content шаблона проверяется теми же `validateContent`, `parts.json`,
  `widgets.json`, что и страница;
- `slotIndex` — целое, `0 <= slotIndex <= content.length`;
- имя — после `trim`, 1–100 символов, уникально в сайте;
- ошибки content — `details: [{ path, code, message }]`, пути `template.content[i]...`;
- ошибки имени — `fields: { name: '...' }`;
- 409 коды: `template_conflict` (с текущими `version`/`updatedAt`),
  `default_template_changed`, `system_template`, `default_template`,
  `template_in_use` (со списком страниц);
- ошибка сохранения не должна оставлять частично применённые изменения.

- `renderSite`/`hydrateSite` импортируют `site-templates.mjs` и передают `templates`.

### 7.6. Ручные визуальные проверки

Браузер запускает пользователь; агент не использует headless/E2E.

Проверить:

- админка: список/редактор шаблонов, создание, переименование, удаление,
  default-селектор, предупреждение о влиянии на страницы;
- редактор страницы: полная страница, границы шаблона, warning-иконка и тултип,
  редактирование props, отсутствие add/remove/move у шаблонных блоков;
- черновики: Cancel, смена шаблона при dirty, Save, ошибка, конфликт версии;
- футер: диалог из шаблона и из страницы, сохранение, отмена, отражение в
  предпросмотре;
- публичный сайт: страница с default/явным/none, с футером и без, с шапкой;
- брендинг: fixed в правом нижнем углу, не перекрывает важные элементы, safe-area,
  клавиатурный фокус;
- темы: страница с другой темой; шапка/футер остаются в глобальной теме;
- SPA-переходы и Back/Forward;
- опубликованный HTML без JS, предпросмотр, публикация и откат;
- ширины 320, 375, 768, 1024 px и десктоп; отсутствие горизонтального переполнения.

## 8. Критерии приёмки

1. В основном меню есть «Шаблоны»; список показывает основной шаблон, default и
   использование; основной шаблон нельзя удалить.
2. Дополнительные шаблоны создаются, редактируются, удаляются; удаление
   используемого/default шаблона блокируется с понятным сообщением.
3. Шаблон хранит последовательность блоков и `slotIndex`; слот нельзя удалить,
   продублировать, переместить или отредактировать.
4. Страница имеет режимы `inherit`, `template`, `none`; `inherit` следует
   default-шаблону; `none` не рендерит шаблон.
5. Редактор страницы показывает блоки шаблона до/после content страницы; у них
   можно менять props, но нельзя добавлять/удалять/перемещать.
6. У каждого шаблонного блока в редакторе страницы постоянно видима яркая
   warning-иконка; по hover/focus показывается точный тултип с именем шаблона.
7. Изменения props шаблонного блока сохраняются в `page_templates`, не в
   `pages.content`; content страницы остаётся отдельным.
8. Черновики, Cancel, Save, dirty state и navigation guard работают; публикация
   блокируется при несохранённых изменениях; конфликт версии шаблона не
   перезаписывает чужие изменения.
9. Футер переведён на `@kroy/footer` + виджет; настройки и данные
   `footer_settings` сохранены; отдельной страницы `/admin/footer` нет; футер
   настраивается из редактора шаблона/страницы.
10. Добавлена запчасть `@kroy/header` с минимальными настройками; отдельного
    рендерера шапки/футера нет.
11. Брендинг «Создано на Oysite» — отдельный обязательный fixed-элемент, не
    часть футера, не отключается, не перекрывает критичные элементы на мобильных.
12. SSR и первая клиентская разметка совпадают; статическая сборка включает
    шаблоны; SPA-переходы и Back/Forward показывают правильный шаблон; сохранённый
    предпросмотр работает.
13. Публикация и откат работают; изменение общего шаблона отражается на всех
    использующих его страницах после публикации; fingerprint учитывает шаблоны.
14. Темы и `pages.appearance` продолжают работать; рекомендация — шаблонные
    блоки в глобальной теме, content — в теме страницы; футер сохраняет
    глобальную тему.
15. Существующие сайты мигрируют без потери данных; основной шаблон создаётся
    автоматически; опубликованные релизы не ломаются до перепубликации.
16. Все обязательные unit/компонентные/SSR-тесты проходят; не добавлены E2E,
    Playwright, браузерная автоматизация и новые тестовые зависимости.
17. Обновлены требования, arch-rules, architecture и профильные справочники
    после согласования решений.

## 9. Реальные технические риски и вопросы, требующие решения

### 9.1. Решения, которые нельзя принимать молча

| № | Вопрос | Варианты | Рекомендация |
|---|---|---|---|
| 1 | Где хранить данные футера | A. `sites.footer_settings` (текущее); B. props блока `@kroy/footer` | **A**: сохраняет API, UUID-ссылки, публичную модель и юридические данные; B — только если нужен полностью независимый футер в каждом шаблоне |
| 2 | Тема шаблонных блоков | A. Глобальная тема для before/after; B. Тема страницы для всего | **A**: сохраняет текущее поведение футера и смысл «оболочки сайта»; B проще, но меняет оформление футера на страницах с appearance |
| 3 | Навигация шапки | A. Использовать `footer.navigation`; B. Собственный список страниц в props шапки | **A** для MVP: без нового поля и UUID в публичном content; B — если нужна независимая навигация, потребуется `page-list`-поле и подготовка данных |
| 4 | Инвариант «основной шаблон всегда есть» | A. Создание в миграции/createSite/seed, `NULL default` = system; B. `AFTER INSERT` триггер | **A** как минимальное; B — если нужна жёсткая гарантия БД; триггер станет первым в схеме |
| 5 | Удаление используемого шаблона | A. Только блокировка с 409; B. Массовый перенос страниц на другой шаблон | **A** для MVP; B — отдельное подтверждаемое действие, если понадобится |
| 6 | Шаблоны для `list`/`detail` | A. Для всех типов; B. Только `standard` | **A**: тип страницы ортогонален; detail-материалы наследуют шаблон detail-страницы; B — непоследовательно и потребует исключений |
| 7 | Шапка/футер в content страницы | A. Разрешить как обычные запчасти; B. Скрыть в PartPicker страницы, оставить только в шаблоне | **B** для UX: меньше случайных дублей; но это небольшое специальное правило. Если «любая запчасть» важнее — A |
| 8 | Сохранение футера | A. Отдельный диалог/`PATCH /api/site/footer`; B. Включить в общий `PUT` страницы | **A**: сохраняет контракт и не смешивает сайтовые данные с content; B — если нужен один общий Save |
| 9 | Конфликты общего шаблона | A. Optimistic lock по `version` + 409; B. Last-write-wins | **A**: общий шаблон влияет на много страниц, потеря правок дороже конфликта; UI должен понятно перезагружать |
| 10 | Публичный реестр шаблонов | A. Отдельный `site-templates.mjs`; B. Встраивать before/after в каждую страницу | **A**: без дублирования bundle; B проще, но растёт HTML/JS |

### 9.2. Технические риски

1. **Потеря правок общего шаблона.** Два редактора страниц могут менять один
   шаблон. Optimistic lock предотвращает молчаливую перезапись, но требует
   понятного UI конфликта и перезагрузки. Автоматического merge нет. Повтор
   запроса после потерянного ответа может получить 409, хотя изменение уже
   сохранено; редактор должен перезагрузить состояние, а не слепо повторять
   запись.
2. **Атомарность сохранения.** Если content страницы и шаблон сохраняются
   разными запросами, возможна частичная запись. Рекомендуется один `PUT` с
   транзакцией; отдельный футер-диалог — осознанное исключение.
3. **Тема и DOM-обёртки.** Вложенные `SiteTheme` могут изменить `:first-child`
   отступы секций и повлиять на фон. Нужны ручные проверки; при проблемах
   придётся либо принять глобальную тему для всех блоков, либо менять CSS
   точечно.
4. **Публичный bundle.** Если шаблон встроить в каждую страницу, размер
   `site-pages.mjs`/HTML вырастет. Отдельный реестр обязателен для сайтов с
   большим шаблоном и многими страницами.
5. **Detail-страницы материалов.** Материалы копируют content detail-шаблона;
   нужно не забыть `templateIndex` и сбор запчастей из шаблона. Иначе detail-
   страницы потеряют шапку/футер или получат неизвестные запчасти.
6. **Опубликованные релизы и миграция.** После миграции старый релиз продолжает
   работать; новая разметка появится только после публикации. Это нужно явно
   сообщить пользователю; автоматической перепубликации нет.
7. **Удаление шаблона и корзина.** Если учитывать только активные страницы,
   восстановление удалённой страницы может ссылаться на удалённый шаблон.
   Рекомендуется блокировать удаление при любых ссылках, включая корзину.
8. **Смена шаблона по умолчанию.** Может изменить много страниц сразу. Нужно
   подтверждение и показ количества `inherit`-страниц; сервер не должен делать
   это «тихо».
9. **Устаревший предпросмотр.** Если default/шаблон изменился в другой вкладке,
   открытый редактор показывает старое. `expectedDefaultTemplateId` и
   `expectedVersion` должны давать 409, а не сохранять устаревшее.
10. **Шапка без собственной навигации.** Использование `footer.navigation`
    связывает шапку и футер. Это может быть неожиданно; нужно подтвердить
    продуктово. Альтернатива — отдельное поле ссылок, но это новый тип поля и
    больше изменений.
11. **Брендинг поверх контента.** Fixed-элемент всегда что-то перекрывает.
    Компактный размер, safe-area и резерв нижнего отступа снижают риск, но
    гарантировать отсутствие наложения на любой пользовательский контент нельзя;
    нужна ручная проверка на 320/375 px.
12. **Миграция и тестовые сайты.** Прямые `INSERT INTO sites` в тестах/скриптах
    не создадут системный шаблон. Либо обновить все пути создания, либо добавить
    триггер. Отдельное окно риска — старый код между миграцией и деплоем: созданный
    им сайт не получит системный шаблон. Нужно либо не создавать сайты в этом
    окне, либо использовать триггер/ленивое создание. Сборка должна падать с
    понятной ошибкой, а не молча терять футер.
13. **Валидация `slotIndex`.** При перемещении/вставке легко получить рассинхрон
    индекса и массива. Все операции должны идти через helpers с unit-тестами;
    API повторно проверяет индекс.
14. **Совместимость API.** `PUT /api/pages/:id` расширяется, но старый формат
    `{ content }` должен работать. `PATCH` не должен принимать поля шаблона, чтобы
    не появилось два способа сохранения.
15. **Права доступа.** Отдельной роли для шаблонов не вводится; используется
    существующая роль администратора сайта. Это согласуется с текущей моделью,
    но вопрос прав владельца остаётся открытым в requirements.

### 9.3. Что не входит в текущую задачу

- специальные правовые страницы;
- создание документов из футера;
- модальные редакторы правовых документов;
- генерация юридических текстов;
- отдельный тип страницы для шаблонов;
- отдельный движок/роутер/рендерер шапки и футера;
- E2E, Playwright, браузерная автоматизация и новые тестовые зависимости.

### 9.4. Что нужно подтвердить до реализации

1. Хранение футера: сайтовые настройки (рекомендуется) или props шаблона.
2. Тема шаблонных блоков: глобальная (рекомендуется) или страничная.
3. Навигация шапки: общая с футером (рекомендуется для MVP) или отдельная.
4. Инвариант основного шаблона: создание в приложении или триггер БД.
5. Разрешать ли шапку/футер в content обычной страницы.
6. Удаление используемого шаблона: только блокировка или ещё массовый перенос.
7. Нужен ли отдельный общий Save для футера вместе со страницей/шаблоном.
8. Применять ли шаблоны ко всем `standard`/`list`/`detail` без исключений.

После ответов на эти пункты спецификация обновляется, затем начинается
реализация по этапам 1–7.
